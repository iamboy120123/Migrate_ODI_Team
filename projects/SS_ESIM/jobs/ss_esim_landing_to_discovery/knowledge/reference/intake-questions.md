## 1. ของที่ต้องมีก่อนเริ่ม

| # | ของ | ใครหา | ถ้าไม่มี |
|---|---|---|---|
| 1 | **โฟลเดอร์งาน Blendata** — workflow export JSON + เอกสาร business/test | คน | อ่าน logic ไม่ได้ → หยุด |
| 2 | **ไฟล์ reference SmartExport** จาก ODI repository **ปลายทาง** ที่มีทั้ง Procedure และ Variable อยู่ในไฟล์เดียว | คน (ใน ODI Studio) | **blocker แข็ง** → หยุดที่ I2 แล้วส่งสเปกให้ไปทำก่อน |
| 3 | **โครงสร้างคอลัมน์ของตารางปลายทาง** — ชื่อคอลัมน์ + `nullable` + `data_default` ของทุกตารางที่ `INSERT`/`MERGE` ลงไป | คน (จากฐานข้อมูล / DBA) | **ไม่ใช่ blocker** — ถามที่ I3 ถ้าไม่มีให้เลือกเดาแทนได้ (ต้องยอมรับความเสี่ยง `ORA-00904`/`ORA-01400` ที่จะถูกระบุไว้ในรายงานปิดงาน) |

**สเปกไฟล์ reference — 18 ข้อ** ⚠️ *เพิ่มรายการที่ 5/6 (`WITH`-led SELECT
ล้วน, `BEGIN...END` PL/SQL block เปล่า) ปิดช่องว่างสุดท้ายที่ `knowledge/reference/optional/manual-build-procedure.md` ขั้น 2 เอ่ยถึงไว้เอง
(`DELETE`, `WITH`, `BEGIN` เป็น 3 ตัวอย่างชนิดคำสั่งที่ reference มักไม่มี — รอบแรกของ v14 ปิดไปแล้ว
แค่ `DELETE` กับ `UPDATE`/`SELECT` standalone) และเขียนใหม่รายการ Package (ตอนนี้คือรายการ 9) ให้โยง
Procedure ทั้ง 5 ตัวเข้า step chain เดียวกัน*

*ต้องมี (ขาดข้อใดข้อหนึ่งทำต่อไม่ได้)*

1. **Project 1 อัน** — ใช้ของเดิมหรือสร้างใหม่ชื่อ `REF_TEMPLATE` ก็ได้ (เลี่ยงจุดในชื่อ — ไม่ใช่ข้อห้ามเด็ดขาด แต่ไฟล์จริงไม่มีตัวอย่าง จึงยังไม่เคยทดสอบ)
2. **Procedure A (`REF_TRUNC_INSERT`) มี 2 command line** ตั้ง Technology / Context / Logical Schema เหมือนกันทั้งคู่ — **ก็อปวางได้ตรงๆ** (ไม่มีตารางจริงก็ใช้ได้ นี่คือ mock สำหรับสร้างโครงสร้าง export เท่านั้น ไม่ได้จะรันจริง):
   ```sql
   -- Command line 1 (OrdTrt=10):
   TRUNCATE TABLE REF_TEMPLATE_STG

   -- Command line 2 (OrdTrt=20):
   INSERT INTO REF_TEMPLATE_STG (COL1, COL2)
   SELECT COL1, COL2 FROM REF_TEMPLATE_SRC
   WHERE STATUS = 'A'
   ```
   *ได้:* รูปแบบ multi-line, กฎว่า `OrdTrt` คือตำแหน่งบรรทัด, กฎว่า `SqlIndGrp` ผูกกับชนิดคำสั่ง, และเลข `ITxtOrig` ของ slot `SNP_LINE_TRT.DEF_I_TXT` — ค่า `SqlIndGrp` ของ `TRUNCATE` และ `INSERT`
3. **Procedure B (`REF_DELETE_SELECT`) มี 2 command line** ตั้ง Technology / Context / Logical Schema เดียวกับ Procedure A:
   ```sql
   -- Command line 1 (OrdTrt=10):
   DELETE FROM REF_TEMPLATE_STG WHERE 1 = 0

   -- Command line 2 (OrdTrt=20):
   SELECT 1 FROM DUAL
   ```
   *ได้:* ค่า `SqlIndGrp` ของ `DELETE` และของ `SELECT` แบบ **standalone ใน Procedure**
   (คนละ slot กับ refresh query ของ Variable ในข้อ 7 — Procedure ที่แปลงตรงไม่ได้แล้วต้องทำเป็น
   placeholder no-op ใช้รูปแบบ `SELECT 1 FROM DUAL` นี้เป๊ะ)
4. **Procedure C (`REF_UPDATE`) มี 1 command line**:
   ```sql
   UPDATE REF_TEMPLATE_STG SET COL1 = COL1 WHERE 1 = 0
   ```
   *ได้:* ค่า `SqlIndGrp` ของ `UPDATE` — ไม่เคยมีตัวอย่างในสเปกรุ่นก่อนหน้าเลย
5. **Procedure D (`REF_WITH_SELECT`) มี 1 command line** — เป็น `WITH`-led
   SELECT ล้วน **ไม่มี** `INSERT` ครอบ (ต่างจาก Procedure A/B ที่ `WITH` ถูกครอบด้วย `INSERT` จนคำแรก
   จริงกลายเป็น `INSERT` ไม่ใช่ `WITH`):
   ```sql
   WITH cte AS (
       SELECT 1 AS COL1 FROM DUAL
   )
   SELECT COL1 FROM cte
   ```
   *ได้:* ค่า `SqlIndGrp` ของคำสั่งที่ขึ้นต้นด้วย `WITH` จริงๆ (คำสั่งชนิดนี้ระบุไว้ใน `knowledge/reference/optional/manual-build-procedure.md`
   ขั้น 2 เป็นหนึ่งใน 3 ตัวอย่างที่ reference มักไม่มี คู่กับ `DELETE` และ `BEGIN`)
6. **Procedure E (`REF_PLSQL_BLOCK`) มี 1 command line** — PL/SQL anonymous
   block เปล่าๆ:
   ```sql
   BEGIN
       NULL;
   END;
   ```
   *ได้:* ค่า `SqlIndGrp` ของคำสั่งที่ขึ้นต้นด้วย `BEGIN` — ใช้เวลา Procedure งานจริงต้องเรียก
   stored procedure/package ผ่าน PL/SQL block แทนคำสั่ง SQL ตรงๆ (ตัวอย่างที่ 3 ที่ `knowledge/reference/optional/manual-build-procedure.md`
   ขั้น 2 เอ่ยถึง)
7. **Variable ตัวที่ 1 พร้อม refresh query** — Datatype `Text`, Schema เดียวกับข้อ 2, ช่อง Refreshing ใส่ **ตรงนี้เลย**:
   ```sql
   SELECT TO_CHAR(SYSDATE,'YYYYMMDDHH24MISS') FROM DUAL
   ```
   *ได้:* เลข `ITxtOrig` ของ slot `SNP_VAR.I_TXT_VAR_IN` ซึ่งอ่านจากที่อื่นไม่ได้เลย
8. **Package 1 อัน มี step ต่อกันจริงครบทุกตัวที่สร้างไว้ข้างบน** ลำดับที่ต้องวางในไดอะแกรม Package:

   **Variable (ข้อ 7) → Procedure A (ข้อ 2) → Procedure B (ข้อ 3) → Procedure C (ข้อ 4) →
   Procedure D (ข้อ 5) → Procedure E (ข้อ 6)**

   **ต้องลากเส้น OK สีเขียวเชื่อมกันจริงทีละคู่ตามลำดับข้างบนจนถึง step สุดท้าย** (ห้ามวางแค่ลอยๆ
   ในไดอะแกรมโดยไม่ลากเส้น) — step สุดท้าย (Procedure E) คือ step ปิดท้ายของ package นี้
   *ได้:* กฎ `OkNextStep` / `OkExit` ครบทั้ง step แบบ `V` และ `T` พร้อม step ปิดท้าย, และ**ค่า
   convention จริงของ `SnpStep`** (`FirstUser`, `LastUser`, `IndLogMethod`, `KoExit`, `OkExitCode`)
   ที่อ่านจากที่อื่นไม่ได้เลย — ถ้าไม่ลากเส้นให้ครบทุก step ทุกตัว ทุก step จะกลายเป็น terminal
   แยกกัน อ่านกฎ `OkNextStep`/`OkExit` ไม่ได้ (เหมือนเดิม) **และค่า convention ของ `SnpStep` จะ
   อ่านไม่ได้เลยถ้า package ไม่มี step ต่อกันจริงสักตัว** **[เกิดขึ้นจริงมาแล้ว — reference ที่ได้รับมา
   รอบแรกไม่มี `SnpStep` เลยสักตัว เครื่องมือต้องใช้ literal สำรอง (`KoExit='1'`) จากที่อื่นแทน]**
9. **กด Save ทุก object ก่อน export** — ของที่ยังไม่ save ไม่ติดมาในไฟล์

*ควรมีเพิ่ม — แต่ละข้อปลดล็อกสิ่งที่ตอนนี้ทำไม่ได้*

10. **เส้น KO สีแดง** จาก Procedure step ไป step อีกตัว → ปลดล็อก retry / แตกสาย error ตอนนี้ทำได้แค่ "พังแล้วหยุดทั้ง package"
11. **Procedure อีกตัวที่ชี้ Logical Schema ตัวที่สอง** ← คุ้มที่สุด → ปลดล็อกทาสก์ที่ส่งข้อมูลออกไประบบที่ไม่ใช่ Oracle ซึ่งตอนนี้ถูกตัดออกทุกครั้ง (ไม่มีสคริปต์ตัวอย่าง — เป็นการตั้งค่า Technology/Schema ในหน้าจอ ไม่ใช่ SQL)
12. **Variable ตัวที่ 2 แบบ Numeric มี Default Value** → ปลดล็อกตัวนับ / ค่าตั้งต้น — ไม่ต้องมี refresh query ก็ได้ แค่ตั้ง **Default Value = `0`** ในหน้าจอ
13. **Procedure ที่มีบรรทัดเดียวเป็น `MERGE`** → ยืนยันว่า `OrdTrt=10` คู่กับ `SqlIndGrp=2` ได้แม้เป็น `MERGE` ไม่ใช่ `INSERT` — ก็อปวางได้ตรงๆ:
    ```sql
    MERGE INTO REF_TEMPLATE_TGT t
    USING REF_TEMPLATE_SRC s ON (t.ID = s.ID)
    WHEN MATCHED THEN UPDATE SET t.COL1 = s.COL1
    WHEN NOT MATCHED THEN INSERT (ID, COL1) VALUES (s.ID, s.COL1)
    ```
14. **Mapping ง่ายๆ 1 อัน** source → target ตรงๆ → ปลดล็อกทางเลือกแบบ Mapping-based (ทำในหน้าจอ Mapping ของ Studio ลาก source → target ตรงๆ ไม่มี SQL ให้ก็อป เพราะจุดประสงค์คือทดสอบว่า export component `SnpMapComp`/`SnpMapAttr` ออกมาแบบไหน)

**หมายเหตุ** — ชื่อตาราง `REF_TEMPLATE_STG` / `REF_TEMPLATE_SRC` / `REF_TEMPLATE_TGT` ข้างบนเป็นชื่อ **mock ล้วนๆ ไม่ต้องมีตารางจริงในฐานข้อมูลรองรับ** ODI ยอมให้พิมพ์ SQL ที่อ้างถึงตารางซึ่งยังไม่มีจริงลงใน Procedure ได้ (จะ error ก็ต่อเมื่อกด "Test" หรือรันจริงเท่านั้น) จุดประสงค์ของไฟล์ reference คือให้ได้ **โครงสร้าง export XML ที่ถูกต้อง** ไม่ใช่ให้รันได้จริง — จะเปลี่ยนชื่อเป็นอย่างอื่นก็ได้ตราบใดที่ตั้ง Technology/Context/Logical Schema ให้ตรงกับ repository ปลายทางจริง

*วิธี export*

15. คลิกขวาที่ **Project** → Export → **Smart Export** (ห้ามใช้ Export ธรรมดา — คนละฟอร์แมต ดู `knowledge/reference/odi-object-reference.md`)
16. **ไม่ใส่ export key ไม่เข้ารหัส** — ถ้า `containsCipherText="true"` จะอ่าน SQL ข้างในไม่ได้
17. **export จาก repository ตัวที่จะ import กลับเข้าไปจริง** — dev/uat/prod มี GlobalId ไม่เหมือนกันแม้ connection ชื่อเดียวกัน
18. **ตั้งชื่อให้แยกจากไฟล์ที่ระบบนี้สร้าง** เช่น `ODI_REFERENCE_DEV_20260910.zip` และเก็บแยกโฟลเดอร์

## 2. คำถาม I1–I17

### กฎการถาม — ทำตามตรงตัว

1. **ถามหนึ่งข้อต่อหนึ่งข้อความ** ห้ามยิงทั้งชุดรวดเดียว — กำแพง17 ข้อจะถูกตอบแบบขอไปที ซึ่งได้ package ที่ผิด
2. **ติดเลขทุกครั้ง** `[I5/17]` ให้ผู้ใช้เห็นความคืบหน้า
3. **หาคำตอบเองก่อนถาม** — หลัง I1/I2 มีทั้ง DAG และ reference อยู่ในมือแล้ว อ่านก่อน ถ้าคำตอบอยู่ในนั้นให้เสนอแล้วขอแค่คำยืนยัน การถามสิ่งที่หาเองได้คือการผลักงานคืนให้ผู้ใช้
4. **ทุกคำถามที่ต้องพิมพ์ตอบ ต้องมีตัวอย่างกำกับ**
5. **ติด blocker ให้หยุดทันที** ไม่เดา ไม่หาทางอ้อม ไม่หยิบไฟล์เก่าที่ไม่รู้ที่มามาใช้
6. **ยืนยันสั้นๆ แล้วไปข้อต่อไป** ไม่ต้องอธิบายแผนทั้งหมดซ้ำทุกรอบ
7. **จบครบ 17 ข้อแล้วสรุปเป็นตารางเดียว** ขอ OK รอบสุดท้ายก่อนลงมือ
8. **ศัพท์เฉพาะของ ODI ที่ผู้ใช้อาจไม่คุ้น (Folder, Package, Variable, TRUNCATE-then-INSERT
   ฯลฯ) ต้องอธิบายเป็นภาษาปกติสั้นๆ กำกับไว้ในคำถามเอง ไม่ใช่สมมติว่าผู้ใช้รู้อยู่แล้ว** ถ้าผู้ใช้
   ถามกลับว่าหมายถึงอะไร ให้หยุดอธิบายให้เข้าใจก่อนไปคำถามถัดไป อย่าเดาว่าเข้าใจแล้ว
9. **หนึ่งคำถาม = หนึ่งการตัดสินใจ แม้อยู่ใน Q เดียวกัน** — ถ้า Q ไหนมีมากกว่า
   หนึ่งเรื่องที่ต้องให้ผู้ใช้ตัดสินใจ (เช่น ยืนยันตารางภาพรวม + เลือกทางแก้สำหรับแถวที่มีความเสี่ยง
   + มีหลายแถว/หลายทาสก์ที่ต้องเลือกแบบเดียวกัน) **ห้ามใส่รวมไว้ในข้อความเดียวกันทั้งหมด**
   ต้องแตกเป็นคำถามย่อยแยกกันตามลำดับ ถามทีละอันจนตอบครบก่อนค่อยไปอันถัดไป — ถ้ามีหลายทาสก์
   ที่ต้องตัดสินใจแบบเดียวกัน (เช่น เลือก `DELETE` หรือ `TRUNCATE PARTITION`) ต้องถามแยกเป็น
   คำถามต่อทาสก์ **ห้ามรวมเป็นคำถามเดียวแล้วสมมติว่าคำตอบเดียวใช้กับทุกแถว** เว้นแต่ผู้ใช้ระบุเอง
   ว่า "ใช้แบบเดียวกันทุกแถว" ซึ่งต้องได้รับการยืนยันแบบเจาะจงชื่อทาสก์ทุกตัวที่จะใช้คำตอบนั้นด้วย
   **[เกิดขึ้นจริงมาแล้ว — ที่ I14 เคยถามรวมหลายทาสก์ไว้ในคำถามเดียว ผู้ใช้ตอบ `1` มาแบบไม่รู้ว่า
   หมายถึงแถวไหน ต้องย้อนถามซ้ำ 3 รอบกว่าจะได้คำตอบครบ]**
10. **รูปแบบการให้ตัวเลือกต้องคงที่ตลอดทั้ง 17 ข้อ ห้ามสลับไปมา** — ถ้าคำตอบ
    ที่เป็นไปได้มีจำนวนจำกัดและนับได้ (ปกติไม่เกิน 5-6 ทาง) **ต้องขึ้นเป็นตัวเลือกแบบเลข `1)` `2)`
    `3)` ... ให้เลือกเสมอ** ห้ามใช้คำถามปลายเปิดแบบ "ยืนยันไหมครับ" หรือ "เอาแบบไหนดี" เฉยๆ กับ
    เรื่องที่จริงๆ มีตัวเลือกจำกัดอยู่แล้ว ส่วนคำตอบที่เปิดกว้างจริง (ชื่อไฟล์, path, ชื่อ schema,
    ชื่อ project) ให้พิมพ์ตอบได้ตามปกติ (มีตัวอย่างกำกับตามกฎข้อ 4) — **ห้ามคำถามเดียวกันสลับ
    รูปแบบครึ่งๆ กลางๆ** ระหว่างตัวเลือกเลขกับปลายเปิดกับ yes/no โดยไม่ประกาศ
    **[เกิดขึ้นจริงมาแล้ว — I14 เดิมมีทั้งตารางให้ยืนยันแบบ yes/no, จุดที่ให้เลือกเลข `1/2/3`,
    และจุดที่ถามปลายเปิด ปนกันอยู่ในคำถามเดียว ผู้ใช้ระบุว่าทำให้สับสนว่าจะตอบแบบไหน]**
11. **agent เสนอไอเดียที่เกินขอบเขตตัวเลือกที่มีอยู่ได้เสมอ แต่ต้องแยกจาก "ข้อสรุปที่ผู้ใช้ยืนยัน
    แล้ว" ให้ชัด และห้ามฝังไอเดียนั้นลงในแผน/ไฟล์ผลลัพธ์จนกว่าจะได้รับอนุมัติแยกต่างหาก**
 — ใช้กับทุกคำถามใน I1–I17 ไม่ใช่แค่ I12: ถ้า agent เห็นว่ามีทางที่ดี
    กว่าตัวเลือกที่ให้ไว้ (เช่น ต้องสร้าง object ใหม่ในฐานข้อมูล ต้องเปลี่ยนสถาปัตยกรรม ต้องขอ
    ข้อมูลเพิ่มจากทีมอื่น) ให้เสนอไอเดียนั้นได้เต็มที่ พร้อมระบุชัดว่า **"นี่คือข้อเสนอ รอคุณอนุมัติ
    ยังไม่ใช่ข้อสรุป"** แล้วบันทึกเป็น open item — **ห้ามเขียนลง build spec/SQL/ไฟล์ผลลัพธ์ราวกับ
    ว่าอนุมัติแล้ว** จนกว่าผู้ใช้จะตอบรับแบบเจาะจง (ระบุ Q ที่เกี่ยวข้อง) **[เกิดขึ้นจริงมาแล้ว —
    ผู้ใช้ขอให้ agent ทำงานแบบช่วยคิดไอเดียได้ แต่คนต้องเป็นคน approve ก่อนทุกครั้ง ไม่ใช่ agent
    ตัดสินใจแทนโดยเงียบๆ — ดูตัวอย่างที่ I12 ข้อ 5 และข้อห้ามใน `migration-rules.md` หัวข้อ 7]**
12. **เจอเรื่องใหม่ระหว่างเตรียมคำถามของ Q ที่กำลังถามอยู่ (research แล้วพบ anomaly/ข้อมูลไม่ตรงกัน/
    ความเสี่ยงที่ไม่ได้อยู่ใน template ของ Q นั้น) ห้ามยัดรวมเข้าไปในข้อความเดียวกับคำถามของ Q ที่
    กำลังถามอยู่** — ต้องแยกเป็นคนละข้อความ ถามให้จบเรื่องที่เจอใหม่ก่อน
    (ไม่ต้องติดเลข `[Qn/17]` ถ้าไม่ใช่คำถามที่นับในแผนที่ลำดับ 17 ข้อ — ใช้รูปแบบเดียวกับ "ถามยืนยัน
    (ไม่ใช่คำถามที่นับเลข)" ที่ใช้กับขั้นสรุป business flow) แล้วค่อยกลับไปถามคำถามเดิมของ Q นั้นต่อ
    เป็นข้อความใหม่อีกที **กฎข้อนี้คนละเรื่องกับข้อ 9** — ข้อ 9 ห้ามรวมหลายการตัดสินใจที่เป็นส่วนหนึ่ง
    ของ Q เดียวกันไว้ในข้อความเดียว ส่วนข้อนี้ห้ามเอาเรื่องที่ไม่ได้เป็นส่วนหนึ่งของ Q นั้นเลยมาพ่วง
    **[เกิดขึ้นจริงมาแล้ว — ตอนถาม I4 (วิธี qualify schema + promote-env) เจอระหว่างไล่ตารางว่าชื่อ
    ตารางในไฟล์ SQL กับชื่อในไฟล์ Model reverse-engineer ไม่ตรงกัน 2 ตัว แล้วเอาสองเรื่องนี้ไปพ่วง
    ถามรวมในข้อความเดียวกับตัวเลือกของ I4 ผู้ใช้ทักท้วงว่าต้องถามทีละคำถามเท่านั้น]**
13. **มีค่าที่ยืนยันแล้วอยู่ในมือ (ไม่ใช่ค่าที่ต้องเดา) ต้องใส่ลงไปในสิ่งที่ส่งมอบให้พร้อมใช้ทันที
    ห้ามเว้นว่างไว้ให้ผู้ใช้เติมเอง และห้ามถามยืนยันซ้ำในสิ่งที่ตอบไปแล้วจากขั้นก่อนหน้า**
    — ใช้กับทุกอย่างที่จะให้ผู้ใช้ copy ไปรันตรงๆ (SQL, คำสั่ง, config) ไม่ใช่แค่คำถามใน I1–I17: ถ้า
    ค่านั้นเคยยืนยันแล้วจากขั้นก่อนหน้า (เช่น ชื่อ schema จากไฟล์ reference ที่ตรวจตอน I2) ให้ใส่ค่านั้น
    ลงในสิ่งที่จะให้ผู้ใช้รันเลย ไม่ใช่เสนอเป็น placeholder/ตัวเลือกให้เติมเอง — ถ้าค่านั้นผิดจริง ผู้ใช้แก้ไข
    บรรทัดเดียวแล้วรันซ้ำได้เองอยู่แล้ว เร็วกว่าการย้อนถามซ้ำหลายรอบ **[เกิดขึ้นจริงมาแล้ว — I3 ตรวจ DDL
    แล้วเจอตารางชื่อซ้ำข้าม schema (owner) จริง ทั้งที่มีชื่อ schema ยืนยันแล้วจาก I2 (`SnpPschema.SchemaName`)
    แต่ agent เสนอ query ที่ไม่ใส่ `WHERE owner=` ให้ผู้ใช้เลือกเติมเอง แทนที่จะใส่ค่าที่ยืนยันแล้วให้ตรงๆ
    ทำให้ผู้ใช้ต้องถามซ้ำ 3 รอบกว่าจะได้ SQL ที่ใช้รันได้จริงทันที]**
14. **ทุกคำถามที่ถามผู้ใช้ต้องเป็นภาษาไทยเสมอ** — ใช้กับทุกคำถามไม่ว่าจะอยู่ใน
    I1–I17, คำถามตอนติด blocker/เจอ anomaly ระหว่าง research (ข้อ 12), หรือคำถามที่โผล่ขึ้นมาระหว่าง
    ขั้น build จริง (เช่น การขอค่า `SqlIndGrp` ที่ reference ไม่มีตัวอย่าง) ห้ามถามเป็นภาษาอังกฤษ — ชื่อ
    field/class/คำสั่ง SQL (`SqlIndGrp`, `TRUNCATE`, `SnpStep` ฯลฯ) ยังคงเป็นภาษาอังกฤษได้ตามปกติ
    เพราะเป็นศัพท์เฉพาะที่ไม่มีคำแปล แต่ประโยคอธิบายบริบทและตัวประโยคคำถามเองต้องเป็นภาษาไทยล้วน
15. **คำถามที่มีคำอธิบาย/บริบทยาวก่อนถึงตัวคำถามจริง ต้องแยก "คำถาม + ตัวเลือก" ไปไว้เป็นส่วนท้ายสุด
    ของข้อความเสมอ** — โครงสร้างที่ถูกต้องของข้อความแต่ละครั้ง: (1) อธิบายบริบท/สิ่งที่
    เจอ/เหตุผลที่ต้องถามให้ครบก่อน (2) จบข้อความด้วยบรรทัดคำถามสั้นๆ ตามด้วยตัวเลือกแบบเลข `1)` `2)`
    `3)` ... (ตามรูปแบบข้อ 10) เป็นส่วนสุดท้ายจริงๆ **ห้ามมีข้อความอธิบายเพิ่มเติมต่อท้ายตัวเลือกอีก**
    ห้ามฝังคำถามหรือตัวเลือกไว้กลางย่อหน้าอธิบายเด็ดขาด — เหตุผล: คำอธิบายที่ยาวทำให้ผู้ใช้ต้องไล่หาว่า
    คำถามจริงๆ คืออะไรและมีตัวเลือกอะไรบ้าง **[เกิดขึ้นจริงมาแล้ว — ผู้ใช้ระบุว่า "อธิบายยาวแล้วหาคำถาม
    ไม่เจอ" ให้เอาคำถามพร้อมตัวเลือกไว้ล่างสุดของข้อความเสมอ]**
16. **ทุกครั้งที่ต้องขอให้ผู้ใช้สร้าง/mock อะไรก็ตาม (object ใน ODI Studio, ข้อมูลทดสอบ, ค่า
    config ฯลฯ) ต้องแนบเนื้อหาจริงที่ต้องใช้มาด้วยเสมอ ไม่ใช่อธิบายแค่โครงสร้าง/สิ่งที่ต้องมีแล้ว
    ปล่อยให้ผู้ใช้คิดเนื้อหาเอง** — เช่น ขอให้สร้าง Procedure ทดสอบ ต้องแนบ SQL
    ที่ก็อปวางได้ตรงๆ (ตามที่ทำไว้แล้วในหัวข้อ 1 ของไฟล์นี้), ขอข้อมูลทดสอบ ต้องแนบตัวอย่างแถวข้อมูลจริงให้
    ไม่ใช่แค่บอกว่า "ใส่ข้อมูลตัวอย่างสัก 3 แถว" เฉยๆ — เหตุผล: ถ้าปล่อยให้ผู้ใช้คิดเนื้อหาเอง
    มีโอกาสได้เนื้อหาที่ไม่ตรงกับสิ่งที่ต้องการทดสอบจริง ต้องกลับไปแก้ซ้ำ ทั้งที่ agent รู้อยู่แล้ว
    ว่าต้องการอะไรตั้งแต่ต้น
17. **บันทึกสถานะลง `status/MIGRATION_STATUS.md` ทุกครั้งที่ปิดหนึ่ง Q หรือมีการตัดสินใจ** — ก่อน I9 ให้แสดง
    ตารางสถานะสั้นๆ ในแชตแทน (ยังไม่รู้ path ที่จะเขียน — `knowledge/lessons-learned.md` L36) หลัง I9 เขียนไฟล์ตาม `knowledge/reference/deliverables.md` (หัวข้อ migration-state)
    บันทึกเฉพาะสิ่งที่ผู้ใช้ยืนยันเอง ห้ามบันทึกแทน
18. **ขั้นเสริม S / I17b ไม่นับเป็น `[Qn/17]`** — ใช้ป้าย `[S]`, `[I17b]` และทำตามกฎข้อ 1–16 เหมือน Q ปกติ
    (ถามทีละข้อ, ตัวเลือกเลข, ภาษาไทย, คำถามอยู่ท้ายข้อความ, แทนค่าที่ยืนยันแล้วให้ครบก่อนส่ง SQL ให้ผู้ใช้รัน)
19. **ทุกครั้งที่ขอให้ผู้ใช้เอาไฟล์มาให้ (วาง, export, รัน query แล้วเซฟผล) AI ต้องสร้างโฟลเดอร์ปลายทางให้ก่อน (mkdir -p ใต้ `input/...` หรือ `run_packs/<pack>/`; ห้ามให้ผู้ใช้สร้างเอง) แล้วบอก path เต็มของโฟลเดอร์นั้น พร้อมบอก 5 อย่างเสมอ** 
    (ก) **path เต็มที่ต้องวางไฟล์** — ถ้ามี root จาก I1 ให้ระบุเป็น `<root>\input\...` หรือ `<root>\reference\...` ตามโครงสร้างโฟลเดอร์
    ที่แนะนำ แทนที่จะบอกลอยๆ ว่า "ส่งไฟล์มา" (ข) **ชื่อไฟล์ที่ต้องการ** (ตัวอย่างชื่อจริง) (ค) **ให้ผู้ใช้ตอบยืนยันว่าวางแล้ว**
    ด้วยตัวเลือกเลข เช่น `1) วางแล้ว  2) ยังไม่มีไฟล์นี้  3) วางที่อื่น (พิมพ์ path)` — AI **ห้ามถือว่าไฟล์อยู่ที่นั่นแล้วลงมืออ่าน
    จนกว่าผู้ใช้ตอบยืนยัน** และหลังยืนยันต้องเปิดไฟล์ตรวจว่ามีจริงและอ่านได้ก่อนรายงานผล ถ้าไม่เจอให้บอกว่าไม่เจอที่ path ไหน
    (ง) **ไฟล์นี้คืออะไร และเอามาจากไหน/ทำอย่างไร** — ถ้า export จากระบบอื่น บอกว่าระบบไหนและเมนู/ขั้นตอนเท่าที่รู้จริง (ห้ามเดาชื่อเมนูที่ไม่รู้ — บอกว่าไม่รู้และให้ถามผู้ดูแลระบบนั้น) · ถ้าต้องรัน SQL เพื่อเอาค่ามา ให้เขียนไฟล์ `.sql` ไว้ใน `run_packs/<pack>/` (SELECT เดียว ตามกฎ `.claude/rules/run-pack.md`) แล้วบอก **path ของไฟล์ SQL**, รันที่ไหน/ต่อฐานไหน, export ผลเป็นอะไร (CSV มีหัวคอลัมน์) และวางผลที่ path ไหน — ห้ามแค่บอกให้ "ไปหา query มารัน" (จ) **ถ้าไม่มีหรือหาไม่ได้ ทำอย่างไรต่อ** — บอกว่าเป็น blocker หรือข้ามได้ และผลของการข้าม
    ใช้กับทุกจุดที่ขอไฟล์: I1, I2, I3 (DDL / ผล query), ขั้น S, I10 ข้อ 6, I17b และตอน rebuild/validate
    ไฟล์ที่ผู้ใช้ยืนยันว่า "ไม่มี" ให้บันทึกลง `status/MIGRATION_STATUS.md` ว่าไม่มี ไม่ใช่ถามซ้ำรอบหน้า

20. **ตัวอย่างที่แนบกับคำถามต้องมาจาก path/ค่าจริงที่รู้แล้ว ไม่ใช่ตัวอย่างสมมติ** 
    (ก) **ก่อน I1** — path ที่ผู้ใช้ให้มา (เช่น `...\migrate`) คือเบาะแสแรก ให้ไต่ขึ้นไปหาโฟลเดอร์ตั้งต้นของงาน
    (เช่น `...\example blend data to odi\`) แล้ว **list จริง** หาโฟลเดอร์ที่ดูเป็นโฟลเดอร์งาน (มี `export_workflow*.json` หรือ `input\`)
    ใช้ path ที่เจอจริงเป็นตัวอย่างและเป็นตัวเลือกเลข `1) 2) ... N) path อื่น (พิมพ์ path เต็ม)` ถ้า list ไม่ได้หรือไม่เจอเลย
    ค่อยใช้ตัวอย่างรูปแบบกลางๆ โดยบอกว่าเป็นรูปแบบสมมติ (ข) **หลัง I1** — ตัวอย่างของ I2, I9 ฯลฯ ให้สร้างจาก root ที่ผู้ใช้ตอบ
    (เช่น `<root>\reference\SmartExport.zip`) ห้ามย้อนไปใช้ `D:\projects\...` หรือ `D:\odi\...` ที่เขียนไว้ในเอกสาร
    (ค) path ตัวอย่างในเอกสารนี้ (`D:\projects\blendata\ss_esim` ฯลฯ) เป็นแค่รูปแบบ **ห้ามยกไปแสดงให้ผู้ใช้ตรงๆ**
    **[เกิดขึ้นจริงมาแล้ว — ผู้ใช้ให้ path `D:\work\blendata\migrate` แต่ AI ตอบ I1 ด้วยตัวอย่าง
    `D:\projects\blendata\ss_esim` ผู้ใช้ระบุว่าต้องใช้ตัวอย่างที่อิงจาก path ที่ให้ไป]**
21. **ทุกคำถามที่ต้องการคำตอบมากกว่า ใช่/ไม่ใช่ ต้องอธิบายให้ชัดและบอกวิธีตอบ** — ในข้อความเดียวกับคำถามต้องมี: ต้องการรู้อะไร · เอาไปใช้ทำอะไร /
    ไม่รู้แล้วเกิดอะไร · ตอบแต่ละทางผลต่างกันอย่างไร · และระบุชัดว่าคำถามเป็นแบบ "ใช่/ไม่ใช่" "เลือกเลข" หรือ "พิมพ์ค่า (มีตัวอย่าง)"
    กฎนี้ใช้กับทุกคำถามในโปรเจกต์ ไม่ใช่เฉพาะ I1–I17 (ดู `CLAUDE.md` §6.1)
22. **ถาม-ตอบในแชต แล้ว agent บันทึกเอง** — แสดงคำถามและตัวเลือกในแชต ไม่บอกให้ผู้ใช้ไปเปิดไฟล์อ่าน · ผู้ใช้ตอบแล้ว agent เขียนลง `status/INTAKE.md`, `status/OPEN_DECISIONS.md`, `config/config.json` เองและสรุปว่าแก้อะไร (ดู `CLAUDE.md` §6.1 ข้อ 8)
23. **คำถามแบบเลือกทุกข้อต้องมี [แนะนำ]** — ระบุข้อที่แนะนำ 1 ข้อพร้อมเหตุผลจากข้อเท็จจริงของงานนี้ และเงื่อนไขที่ควรเลือกข้ออื่น ถ้าข้อมูลไม่พอให้บอกว่าขาดอะไร (ดู `CLAUDE.md` §6.1 ข้อ 3)

### [I1/17] โฟลเดอร์งาน Blendata ต้นทาง

**ในโปรเจกต์นี้** root = โฟลเดอร์โปรเจกต์ (มี `input\` อยู่แล้ว) — ไฟล์เก่าจาก Blendata ทั้งหมดอยู่ใต้ `input\blendata\` (รวมโฟลเดอร์ย่อย) — workflow JSON (`export_workflow.json`) · เอกสาร (.md .docx .pdf) · ข้อมูลเทส (.txt .csv) · `expected_results.csv` · `.sql` seed · สคริปต์สร้างข้อมูลเทส — สแกนและจัดประเภทเอง ไม่ต้องถามหา path (ถ้าขาดอะไร ให้บอกผู้ใช้ว่าขาดอะไรและวางที่ `input\blendata\`) · ไฟล์ `.sql` ที่มี DDL/DML = คนรันเอง · root ใช้ต่อที่ I2, I3, I9

**ต้องได้อะไรกลับมา** — path โฟลเดอร์ 1 อัน แล้วต้องเข้าไปดูว่ามีอะไรครบไหม

1. **workflow export JSON** (เช่น `export_workflow*.json`) — **บังคับ** เป็นที่มาของรายการทาสก์, ลำดับ dependency (`parentTask`), SQL และ `sinkOption.mode` — โครงสร้าง field จริง (ต้อง parse JSON ซ้อนสองชั้น) ดูที่ `knowledge/reference/blendata-json-schema.md`
2. **เอกสาร business / test** (`README.md`, design doc) — ควรมี เป็นที่มาของเงื่อนไขธุรกิจ เคสเทส และข้อจำกัดด้านความปลอดภัย
3. **ไฟล์ `.sql` แยก** — ถ้า SQL ไม่ได้ฝังใน JSON
4. **`expected_results.csv` หรือตารางผลที่คาดหวัง** — ถ้ามี ใช้ตอนเทสหลัง import
5. **ไฟล์ข้อมูลเทส** — ไม่จำเป็นต่อการสร้าง package แต่บอกได้ว่าจะเทสอย่างไร

**ต้องทำหลังได้คำตอบ:** list โฟลเดอร์ แล้วรายงานกลับเป็นข้อๆ ว่าเจอไฟล์อะไร ไฟล์ไหนถูกใช้เป็น DAG ไฟล์ไหนถูกมองข้าม — ให้ผู้ใช้ยืนยันว่าอ่านไฟล์ถูกตัว

**ถ้าไม่มี JSON:** ถามหาไฟล์ DAG หรือ `.sql` โดยตรง ถ้าไม่มีทั้งคู่ให้หยุด — ไม่มีอะไรให้แปลง

**ผลถ้าตอบผิด:** แปลงงานผิดตัว หรือได้ทาสก์ไม่ครบโดยไม่มีใครรู้

1. **ทาสก์ที่มี SQL อ่าน/เขียนตาราง** — ตารางต้นทางมาจาก `FROM`/`JOIN` ตารางปลายทางมาจาก

   status) ก็บรรยายตรงจุดที่มันอยู่ในลำดับจริง ไม่ต้องรอไปพูดรวมท้ายสุด — จะระบุสั้นๆ ว่าเป็น

2. **ทาสก์ที่ไม่มี SQL เลย** (recovery, table retention/cleanup, trigger/watcher ฯลฯ) **ก็ต้องมี
   เลขข้อของตัวเองตรงตำแหน่งที่มันรันจริง** บรรยายว่าทำอะไรจากชนิด service/config ที่มี (เช่น

   หัวข้อ "ไม่มี data flow" ต่างหากท้ายข้อความ
3. **จุดที่ DAG แตกสาย/รวมสาย** (ทาสก์เดียวมี `parentTask` มากกว่า 1 ตัว หรือหลายทาสก์มี

### [I3/17] โครงสร้างคอลัมน์ของตารางปลายทาง (DDL) — หรือให้เดา

⚠️ v7 ขอ DDL ไว้เป็นข้อย่อยที่ 5 ของคำถามเรื่อง
ความพร้อม SQL ซึ่ง**ผิดกฎการถามของเอกสารเอง** (ไม่มีตัวอย่างคำตอบ ไม่มีทางออกถ้าไม่มี ไม่มี blocker)
และมาถึงช้าเกินไป — กว่าจะรู้ว่าต้องไปขอ DBA ก็ตอบไปแล้ว 8 ข้อ แก้โดยแยกเป็นคำถามของตัวเอง
แต่ยังบังคับให้ผู้ใช้ไปหา DDL มาให้ได้ไม่ว่ากรณีไหน **ปัจจุบันเป็นทางเลือกจริง** — ถ้าหาไม่ได้
ให้เดาได้ แต่ต้องรู้ตัวว่าเดา ไม่ใช่แกล้งทำเป็นไม่รู้ว่ากำลังเดาอยู่ (ดู `knowledge/reference/spark-to-oracle-sql.md` กฎ D-R1)

**ถ้ามี root จาก I1 และเจอ `reference\ddl\ALL_TAB_COLUMNS*.csv` (หรือ `MFOL_*.xml`)** — อ่านไฟล์นั้นก่อน แล้วเทียบกับรายชื่อตารางที่ SQL เขียนลง/อ่าน
รายงานสั้นๆ ว่าตารางไหนมี DDL แล้ว ตารางไหนยังขาด แล้วถามเฉพาะส่วนที่ขาด (ไม่ถามหา DDL ที่มีอยู่แล้วซ้ำ)

**ถามตรงนี้เพราะสองเหตุผล**

1. **ต้องใช้ก่อนแปลง SQL** — เขียน column list ของ `INSERT` ไม่ได้เลยถ้าไม่รู้ว่าตารางมีคอลัมน์อะไร
   (กฎ D-R1 ใน `knowledge/reference/spark-to-oracle-sql.md` — column list ต้องมีเสมอ ไม่ว่าจะมี DDL จริงหรือต้องเดา)
2. **ผู้ใช้ต้องออกไปหาจากข้างนอก** เหมือน I2 ที่ต้องไป export จาก Studio — ถามตรงนี้แล้วเขา
   เดินไปขอ DBA ได้**ระหว่าง**ตอบ I5–I17 ซึ่งเป็นเรื่องตั้งชื่อล้วนๆ ไม่ต้องออกไปหาอะไรเพิ่ม

**ต้องหาเองก่อนถาม** — ไล่ SQL ทุกทาสก์ แยกเอาเฉพาะ **ตารางที่ถูกเขียน**
(`INSERT INTO` / `MERGE INTO` / `UPDATE`) แล้วแสดงรายชื่อให้ครบในคำถาม
ตารางที่อ่านอย่างเดียว (`FROM` / `JOIN`) **ไม่บังคับต้องมี DDL** แต่ให้ใส่ชื่อไว้ใน query เดียวกันด้วย (ไม่ต้องรันเพิ่ม) เพราะชนิดคอลัมน์ของตารางที่ SQL อ่านแล้วแปลงวันที่/ชนิด ใช้ตัดสินกฎ D-R6/D-R8 และผล query ใช้เช็คชื่อซ้ำข้าม owner ที่ I4 — ถ้าผู้ใช้ส่ง DDL ที่ไม่ครอบคลุมบางตาราง (เช่น ตาราง landing หรือ `ext_*`) ให้บอกว่าตารางไหนยังไม่มี และถามว่าจะเอาไปใส่ใน query นี้เพิ่มไหม

**ถ้าไฟล์ reference ที่ I2 มีโครงสร้างตาราง reverse-engineer (`SnpTable`/`SnpCol`) ติดมาด้วย**
 — ให้เอาชื่อตารางในนั้นมาเทียบกับตารางในรายการนี้ก่อนถามผู้ใช้
**เฉพาะกรณีชื่อตรงกันเป๊ะ (ไม่นับตัวพิมพ์ใหญ่เล็ก)** ถึงจะใช้แทน DDL จริงได้เลย (เสนอแล้วขอแค่
คำยืนยันตามกฎการถามข้อ 3) ถ้าเจอชื่อ**ใกล้เคียงแต่ไม่ตรงเป๊ะ** (เช่นมีคำต่อท้ายเพิ่ม/สะกดต่างกัน)
**ให้ถือว่าตารางนั้นไม่มี DDL เหมือนไม่เจออะไรเลย** ห้ามหยุดถามระหว่างทางว่าจะใช้ชื่อไหน —
แค่บันทึกไว้เป็นโน้ตท้ายรายงานปิดงานว่าเจอชื่อใกล้เคียงอะไรบ้าง เผื่อผู้ใช้อยากเช็คเอง
**[เกิดขึ้นจริงมาแล้ว — ดู `knowledge/lessons-learned.md` L33]**

**ถามว่า:**
> `[I3/17]` ขอโครงสร้างคอลัมน์ของตารางปลายทางครับ — ตารางที่ `INSERT` / `MERGE` ลงไป
> ผมเจอ `<n>` ใบ: `<รายชื่อ>`
>
> ตัวอย่างทำไมเรื่องนี้สำคัญ: ถ้าฝั่งต้นทางใช้ชื่อ `firstName` แต่ตารางปลายทางจริงมีแค่คอลัมน์
> ชื่อ `name` — ถ้าไม่มีโครงสร้างตารางจริงมาเทียบ ผมจะเห็นแค่ `firstName` แล้วเขียน column list
> ผิดชื่อ ทำให้รันแล้วได้ `ORA-00904: invalid identifier`
>
> **1) มีอยู่แล้ว** — ส่งมาได้เลย เอาแบบไหนก็ได้ในสามแบบนี้:
> - **(1) ผลของ query นี้** *(SELECT ล้วน ไม่แตะข้อมูล — สะดวกที่สุดสำหรับผม)*
>   ```sql
>   SELECT owner, table_name, column_id, column_name, data_type, data_length,
>          data_precision, data_scale, nullable, data_default
>   FROM   all_tab_columns
>   WHERE  table_name IN ('<TABLE1>', '<TABLE2>', …)
>   ORDER  BY table_name, owner, column_id;
>   ```
>   *(ตั้งใจไม่ใส่ `owner=` — เพื่อให้เห็นว่าชื่อตารางเดียวกันอยู่หลาย owner ไหม ซึ่งเคยทำให้ SQL รันผ่านแต่ได้ 0 แถวเงียบๆ ถ้ามีหลาย owner ผมจะถามที่ I4 แยกต่างหาก)*
>   *(ใส่ชื่อตารางที่ DAG แตะถึงทุกตัวใน `IN (...)` ได้เลย ทั้งตารางที่เขียนและตารางที่อ่านอย่างเดียว — รันครั้งเดียวได้ข้อมูลครบ ไม่ต้องรันเพิ่มที่ขั้นอื่น)*
> - **(2)** สคริปต์ `CREATE TABLE` ของตารางเหล่านี้
> - **(3)** ผล `DESCRIBE <table>` ทีละใบ
>
> **2) ไม่มี และไม่สะดวกไปหา** — ให้ผมเดาชื่อคอลัมน์ปลายทางจากชื่อ field/alias ฝั่งต้นทางแทน
> ผมจะทำ column list ให้ครบตามจำนวนที่ `SELECT` ส่งไปเสมอ (กฎ D-R1 ยกเว้นไม่ได้) แต่ **ชื่อที่ใช้
> เป็นการเดา ไม่ใช่ชื่อที่ยืนยันแล้ว** และถ้าตารางจริงมีคอลัมน์ `NOT NULL` ที่ฝั่งต้นทางไม่มีข้อมูล
> ส่งมาเลย ผมไม่มีทางรู้ล่วงหน้าว่าคอลัมน์นั้นมีอยู่ — ทุกตารางที่ใช้โหมดนี้จะถูกระบุชัดเจนเป็น
> **"เดา — ยังไม่ยืนยัน"** ในรายงานปิดงาน ไม่ใช่ปล่อยผ่านเงียบๆ

*(ถ้าตอบ 1 ตอนนี้แล้วนึกออกว่าจริงๆ ไม่มี หรือตอบ 2 ไว้แล้วหาที่หลังได้ ก็เปลี่ยนคำตอบได้ตลอดก่อน
เริ่มประกอบไฟล์จริง — คำถามนี้ไม่ใช่ blocker แข็งแบบ I2)*

**ต้องได้อะไรกลับมา — ถ้าตอบ 1 (มี DDL จริง)**

1. **ชื่อคอลัมน์ทุกตัวของทุกตารางปลายทาง** — นี่คือของที่ขาดไม่ได้ ใช้เขียน column list
2. **`nullable` และ `data_default` ของแต่ละคอลัมน์** — **อย่าขอแค่ชื่อ**
   ขอแค่ชื่อจะปิด `ORA-00947` ได้จริง แต่ไปเปิดช่อง **`ORA-01400: cannot insert NULL`** แทน
   เพราะคอลัมน์ที่เราไม่ได้ใส่ในลิสต์จะได้ `NULL` ถ้าคอลัมน์นั้นเป็น `NOT NULL` และไม่มี
   `DEFAULT` จะพังตอนรัน สองค่านี้คือสิ่งเดียวที่บอกได้ล่วงหน้า
3. **`data_type`** — ใช้เตือนตอนเห็นการแปลงที่น่าสงสัย (เช่น literal string ลงคอลัมน์ `NUMBER`)
   ไม่ใช่ของบังคับ แต่ได้มาฟรีจาก query เดียวกัน
4. **ยืนยันว่าตารางครบทุกใบ** — ถ้ารายการที่ผู้ใช้ส่งมามีไม่ครบตามที่ AI ไล่ได้จาก SQL
   ต้องบอกว่าขาดใบไหน — ใบที่ขาดให้ถือว่าตอบ 2 (เดา) เฉพาะใบนั้น ห้ามเดาโครงสร้างเองแล้วสวมรอย
   ว่าเป็นของจริง

**เก็บเป็นไฟล์** — ถ้ารัน python ได้ ให้เซฟผลเป็น CSV (เช่น `target_columns.csv`) แล้วส่งเข้า
`python scripts/checks/check_sql.py <โฟลเดอร์ sql> --ddl target_columns.csv` ซึ่งจะตรวจให้อัตโนมัติว่า
ชื่อในลิสต์มีจริงไหม และมีคอลัมน์ `NOT NULL` ตัวไหนตกหล่นไหม (ดู `README.md`)
ถ้าทำเป็นไฟล์ไม่ได้ วางเป็นตารางในแชทก็ใช้ได้ แค่ต้องไล่ด้วยตาแทน

**ถ้าตอบ 2 (เดา)**

- ใช้ชื่อ field/alias ฝั่งต้นทางเป๊ะๆ เป็นชื่อคอลัมน์ปลายทาง **ห้ามเดาไกลไปกว่านั้น** (เช่น ห้ามลอง
  เปลี่ยนรูปแบบชื่อเอาเอง เดาแค่ "เอาชื่อที่มีอยู่มาใส่" เท่านั้น เพราะไม่มีข้อมูลอะไรให้เดาแม่นกว่านี้)
- column list ต้องยังมีครบตามจำนวน `SELECT` เสมอ (กฎ D-R1 ไม่มีข้อยกเว้น)
- ทุก `INSERT` ที่ใช้โหมดนี้ ให้ใส่คอมเมนต์ SQL กำกับไว้ในบรรทัดนั้น เช่น
  `-- GUESSED COLUMN LIST: no DDL provided, names copied from source, not verified against dssdev.<table>`
  เพื่อให้คนที่มารีวิวเห็นได้ทันทีโดยไม่ต้องเปิดรายงานปิดงานควบคู่
- บันทึกตารางที่ใช้โหมดนี้ทุกใบไว้ในแผนการสร้าง (build spec) และจะถูกยกมาย้ำอีกครั้งที่ **I14**
  ก่อนสร้างไฟล์จริง — ไม่ใช่จุดหยุด แต่เป็นจุดให้ยืนยันครั้งสุดท้ายว่ายอมรับความเสี่ยงนี้

**ถ้าตารางยังไม่ถูกสร้างในฐานข้อมูลปลายทาง** — ต้องรู้ให้ได้ตรงนี้ ไม่ใช่ไปเจอตอนรัน
ถามว่าใครสร้างและจะเสร็จเมื่อไร แล้วบันทึกเป็น open item (`knowledge/reference/validation-and-cutover.md` ข้อ 7 ถามเรื่องนี้ไว้แล้ว)
**ห้าม AI เขียนหรือรัน `CREATE TABLE` ให้เอง** — ข้อห้ามเด็ดขาดข้อแรกใน `migration-rules.md` หัวข้อ 7

**ขอบเขตของ I3 ไม่ใช่แค่ตารางที่ `INSERT`/`MERGE` ลงไปเท่านั้น** — ต้องรวม
**ตารางฝั่ง READ ที่เอาไปใช้กับ `TO_DATE`/`TO_TIMESTAMP`/`TO_NUMBER` หรือเทียบกับคอลัมน์ชนิดวันที่**
ด้วย (เช่น ตาราง/view ภายนอกที่เอาคอลัมน์ไปใส่ใน `TO_DATE(x)` หรือเทียบกับผลลัพธ์ `TRUNC(...)`)
แม้จะเป็นฝั่ง READ ล้วนไม่มีการ `INSERT` เข้าไปเลยก็ตาม — ถ้าไม่รู้ชนิด/format จริงของคอลัมน์เหล่านี้
`TO_DATE`/`TO_TIMESTAMP` ที่ไม่มี format mask จะพึ่งพา NLS ของ agent เงียบๆ (checklist ข้อ 43,
`knowledge/reference/spark-to-oracle-sql.md` rule D-R6) — ถามรวมไปกับ I3 เป็นคำถามเดียวกัน ไม่ต้องแยกเป็นคำถามใหม่ **[เกิดขึ้นจริง
มาแล้ว — I3 ถามแค่ตาราง `INSERT`/`MERGE` ทำให้ view ภายนอกที่ใช้ใน `TO_DATE` หลุดไป ต้องกลับมา
ถามผู้ใช้กลางรอบ build จริงว่าจะใส่ format mask อะไรดี]**

**ผลถ้าไม่ถามเลย (ข้ามคำถามนี้ไปทั้งหมด)** — คือสิ่งที่เกิดกับ `050100` ในงานจริง: เขียน `INSERT`
แบบไม่มี column list เพราะไม่มีข้อมูลจะเขียน แล้วตายด้วย `ORA-00947` ตอนรัน **[เกิดขึ้นจริงมาแล้ว]**
การเลือกตอบ 2 (เดา) ต่างจากการไม่ถามเลย ตรงที่อย่างน้อย column list จะครบเสมอและความเสี่ยง
ที่เหลือ (`ORA-00904` / `ORA-01400`) ถูกเปิดเผยไว้ล่วงหน้าแล้ว ไม่ใช่มาเจอเอาตอนรันแบบไม่มีใครรู้ตัว

### [I4/17] Oracle schema ของตาราง และวิธี qualify

⚠️ **คำถามนี้มีเพราะเกิดปัญหาจริง** — package ที่สร้างออกมามี SQL ที่เขียน
ชื่อตารางเปล่าๆ (`tb_transaction_ss_esim_valid`) แล้ว**ผู้ใช้ต้องมานั่งเติม `dssdev.` เองทีละจุด
ก่อนจะรันได้** **[เกิดขึ้นจริงมาแล้ว]**

**ต้องเข้าใจให้ตรงก่อน — สามคำนี้คนละเรื่องกัน**

| คำ | คืออะไร | ตัวอย่าง |
|---|---|---|
| **Folder** (I7) | กล่องจัดกลุ่มข้างใน ODI project | `First Folder` |
| **Logical Schema** | ชื่อที่ ODI ใช้เรียก connection ปลายทาง อยู่ในช่อง `DefLschemaName` ของทุกบรรทัดคำสั่ง | `DSSDEV` |
| **Oracle schema** ← *ข้อนี้ถามตัวนี้* | เจ้าของตารางจริงในฐานข้อมูล ตัวที่ต้องไปเป็น prefix ใน SQL | `dssdev.tb_xxx` |

**ทำไม ODI ไม่เติมให้เอง** — ช่อง `LocObjPattern` ของ Physical Schema เป็น `%SCHEMA.%OBJECT`
ก็จริง แต่ pattern นั้นใช้กับ **Knowledge Module และ Datastore เท่านั้น** SQL ดิบที่พิมพ์ลงใน
Procedure command line ถูกส่งไปที่ฐานข้อมูล**ตรงๆ ไม่มีการแทนที่ใดๆ** ตารางที่ไม่ qualify จึงไป
resolve ตาม default schema ของ **user ที่ Data Server ใช้ต่อ** ไม่ใช่ตาม Physical Schema ที่ตั้งไว้
— ในไฟล์ที่ทดสอบ user คือ `system` ส่วนตารางอยู่ใน `DSSDEV` จึงหากันไม่เจอ **[เห็นในไฟล์จริง]**

**ต้องหาเองก่อนถาม — อ่าน 4 ค่านี้จาก reference แล้วเอามาแสดง**

| ค่า | อ่านจาก | ใช้ทำอะไร |
|---|---|---|
| `SnpPschema.SchemaName` | topology | **ค่าเสนอเริ่มต้นของ schema** |
| `SnpPschema.WschemaName` | topology | schema สำหรับตารางชั่วคราว (ปกติเท่ากัน — ถ้าไม่เท่าต้องถาม) |
| `SnpConnect.UserName` | topology | user ที่ต่อจริง — **ถ้าไม่เท่ากับ `SchemaName` แปลว่าไม่ qualify แล้วจะหาตารางไม่เจอแน่นอน** |
| `SnpConnect.OnConCmd` | topology | ถ้าไม่ใช่ null แปลว่ามีคำสั่งรันตอนต่อ connection อยู่แล้ว ต้องอ่านว่าตั้ง `CURRENT_SCHEMA` ไว้หรือเปล่า |

แล้วไล่ SQL ทุกทาสก์เก็บ **รายชื่อตารางที่อ้างถึงทั้งหมด** (ตามหลัง `FROM` / `JOIN` /
`INSERT INTO` / `MERGE INTO` / `TRUNCATE TABLE` / `UPDATE`) จัดกลุ่มตาม prefix ของชื่อ
แล้วเอามาแสดงในคำถาม — **ห้ามถามลอยๆ ว่า "ใช้ schema อะไร"**

**ใช้ผล query ของ I3 ด้วย (ถ้ามี)** — ดูคอลัมน์ `owner` ในผลของ I3: ถ้าชื่อตารางตัวไหนโผล่มากกว่าหนึ่ง `owner` (เช่นมีสำเนาใน `SYSTEM` และตัวจริงใน schema อื่น) ให้บอกผู้ใช้เป็นข้อความแยกก่อนถามตัวเลือกของ I4 (กฎการถามข้อ 12) และบันทึกลง `status/MIGRATION_STATUS.md` — ถ้า login (`SnpConnect.UserName`) ไม่เท่ากับ owner ตัวจริง SQL ที่ไม่ qualify จะอ่านสำเนาแล้วได้ 0 แถวโดยไม่มี error ถ้าผู้ใช้ข้าม I3 หรือไม่มีผล query ให้บันทึกว่า "ยังไม่ได้ตรวจตารางซ้ำข้าม owner" เป็นสมมติฐานที่ยังไม่ยืนยัน

**ถามว่า:**
> `[I4/17]` Oracle **schema** ที่ตารางของงานนี้อยู่ครับ — ตัวที่จะไปเป็น prefix ใน SQL
> (`dssdev.tb_xxx`) คนละตัวกับ Logical Schema ของ ODI นะครับ
>
> จาก reference ผมอ่านได้ว่า Physical Schema คือ `<SchemaName>` และ user ที่ต่อคือ
> `<UserName>` — ขอเสนอ `<schemaตัวเล็ก>.` ตาม house style ที่ใช้ตัวพิมพ์เล็ก
>
> จาก SQL ทั้งหมดผมเจอ `<n>` ตาราง แบ่งได้เป็น
> - `<k>` ตาราง `<prefix ร่วม>` → ใช้ `<schema>` ใช่ไหมครับ
> - `<m>` ตาราง `<ชื่อที่ดูต่างออกไป>` → อยู่ schema เดียวกันไหม หรือคนละที่
>
> และอีกเรื่องหนึ่ง: ตอน promote ไป UAT/PROD ชื่อ schema เปลี่ยนไหมครับ
> 1) ชื่อเดียวกันทุก env → ฝัง `<schema>.` ลงใน SQL ได้เลย (ผมแนะนำแบบนี้)
> 2) เปลี่ยนตาม env → ไม่ฝังใน SQL แล้วให้ทีมไปตั้ง `CURRENT_SCHEMA` ที่ Data Server แทน

**ต้องได้อะไรกลับมา 4 อย่าง**

1. **ชื่อ schema หลัก** และรูปแบบตัวพิมพ์ที่จะใช้ (house style คือตัวพิมพ์เล็ก — Oracle ไม่สนตัวพิมพ์
   ถ้าไม่ใส่ double quote แต่ให้เขียนเหมือนกันทั้งไฟล์)
2. **รายการตารางที่อยู่คนละ schema** — ตารางที่ชื่อขึ้นต้นต่างจากกลุ่มหลัก (เช่นขึ้นต้น `ext_`
   หรือ `vw_`) ต้องถามแยกทุกตัว **ห้ามเหมาว่าอยู่ schema เดียวกันทั้งหมด** ถ้ามีหลาย schema
   ต้องได้ตาราง `ตาราง → schema` ครบทุกแถวก่อนไปต่อ
3. **วิธี qualify — เลือกหนึ่งข้อ**

   | # | วิธี | ข้อดี | ข้อเสีย |
   |---|---|---|---|
   | **1** *(default)* | เขียน `schema.table` ลงใน SQL ตรงๆ ตอนแปลง | ชัดเจน รีวิวได้ ไม่ต้องแตะ topology เห็นด้วยตาว่าชี้ไปไหน | promote ข้าม env ต้องแก้ SQL ถ้าชื่อ schema เปลี่ยน |
   | **2** | ปล่อยไม่ qualify แล้วให้คนไปตั้ง `ALTER SESSION SET CURRENT_SCHEMA=<schema>` ที่ Data Server (ช่อง `OnConCmd`) | SQL ตัวเดียวใช้ได้ทุก env | เป็นการตั้งค่านอกไฟล์ที่คนต้องไปทำเอง · มองจาก SQL ไม่ออกว่าวิ่งไปไหน · กระทบทุกอย่างที่ใช้ Data Server ตัวนั้น |
   | **3** | ใช้ ODI substitution (`odiRef`) ให้เติม schema ตอนรัน | ได้ทั้งความชัดและความพกพา | **เอกสารชุดนี้ไม่มีตัวอย่างและไม่เคยทดสอบ** reference ก็ไม่มีให้ดูรูปแบบ → ถ้าผู้ใช้เลือกข้อนี้ ต้องบอกตรงๆ ว่าเป็นทางที่ยังไม่มีใครเดิน แล้วให้เขาตัดสินอีกครั้ง |

4. **ถ้าเลือกข้อ 2** ต้องบันทึกเป็น **open item ในรายงานปิดงาน** ว่าคนต้องไปตั้งค่าที่ Data Server
   ก่อนรัน มิฉะนั้น package จะ import ผ่านแล้วพังตอนรันด้วย `ORA-00942: table or view does not exist`

**ถ้าผู้ใช้ตอบไม่ได้** — อย่าเดา ให้ไปดูจาก DDL ของตารางจริง หรือถามทีม DBA แล้วหยุดรอ
การเติม schema ผิดตัวทำให้ **import ผ่าน แต่รันแล้วอ่านตารางผิดใบ** ซึ่งแย่กว่าหาตารางไม่เจอ

**ผลถ้าตอบผิดหรือไม่ถาม** — `ORA-00942: table or view does not exist` ตอนรัน step แรกที่แตะ
ตารางจริง หรือ (แย่กว่า) เจอตารางชื่อเดียวกันใน schema อื่นแล้วประมวลผลข้อมูลผิดชุดเงียบๆ

**ต้องตรวจตอนท้าย** — หลังประกอบไฟล์แล้ว ชื่อตารางทุกตัวใน SQL ต้อง qualify ครบ
(ยกเว้น `DUAL` และ alias/inline view) ดู `knowledge/reference/delivery-checklist.md` checklist ข้อ 31

### [I10/17] ความพร้อมของ SQL

**ถามว่า:**
> `[I10/17]` SQL ในงานนี้แปลงเป็น Oracle แล้วหรือยังเป็น Spark SQL อยู่
> ผมสแกนดูแล้วเจอ `<รายการ Spark-ism ที่พบ>` — ดูเหมือน `<ยังดิบ / แปลงแล้ว>`
> ยืนยันได้ไหมครับ และเคยเอาไปรันจริงกับ Oracle dev แล้วหรือยัง

**ต้องได้อะไรกลับมา 5 อย่าง (+ ข้อ 6 ถามเฉพาะเมื่อเข้าเงื่อนไข)**

1. **SQL เป็นภาษาอะไรแล้ว** — Spark ดิบ หรือแปลงเป็น Oracle แล้ว
2. **ถ้าแปลงแล้ว: เคยรันจริงกับ Oracle หรือยัง** — ถ้ายัง ต้องเตือนว่า import จะผ่านแต่จะไปพังตอนรัน เพราะการตรวจไฟล์ตรวจแค่โครงสร้าง XML ไม่ได้ตรวจ SQL
3. **SQL อยู่ที่ไหน** — ฝังใน DAG JSON, ไฟล์ `.sql` แยก, หรืออยู่ใน reference (กรณีงานพี่น้องกับที่ migrate ไปแล้ว)
4. **มีอักขระนอก ISO-8859-1 ไหม (คอมเมนต์ภาษาไทยนับด้วย)** — ไฟล์ SmartExport ประกาศ encoding เป็น ISO-8859-1 และ export จริงเป็น ASCII ล้วน ไม่มีตัวอย่างว่า ODI เขียนอักขระนอกชุดนี้ยังไง **ต้องหลีกเลี่ยง ไม่ใช่หาทาง escape** — `&#NNNN;` ไม่ถูกตีความข้างใน CDATA จะกลายเป็นข้อความดิบ **[พิสูจน์แล้ว]**
   - ต้องสแกนหาเองก่อนถาม แล้วรายงานว่าเจอที่ไฟล์ไหน บรรทัดไหน
   - ทางแก้: เปลี่ยนคอมเมนต์เป็นอังกฤษ หรือถอดคอมเมนต์นั้นออก
5. **DDL ของตารางปลายทาง — สถานะแต่ละใบเป็นยังไง** ถามไว้แล้วที่ **I3** — ยืนยันอีกรอบว่าใบไหน
   ได้ DDL จริงแล้ว ใบไหนตกลงใช้โหมดเดา ใบไหนยังไม่ตัดสินใจ (ใบที่ยังไม่ตัดสินใจต้องทวงตรงนี้
   อีกรอบว่าจะรอ DDL ต่อ หรือจะเปลี่ยนไปใช้โหมดเดา) **ห้ามข้ามไปโดยไม่ระบุสถานะ** และ **ห้ามเขียน
   `INSERT` ที่ยังไม่รู้สถานะแล้วบอกว่า "เดี๋ยวไปเจอตอนรัน"** — ต้องเลือกอย่างใดอย่างหนึ่งเสมอ

6. **เวอร์ชัน Oracle และ timezone ของ DB** — ถามเป็นข้อความแยกหลังปิดข้อ 1–5 (กฎการถามข้อ 9 และ 12)
   - **เงื่อนไข (a) ต้องถามเวอร์ชัน:** SQL มีการ parse text เป็นวันที่ (`to_timestamp`/`to_date` ของ text — กฎ D-R8) เพราะ `DEFAULT NULL ON CONVERSION ERROR` ต้อง Oracle 12.2 ขึ้นไป
   - **เงื่อนไข (b) ต้องถามเวลา:** SQL ใช้ `now()` / `current_timestamp()` (ส่วนที่ตัดช่วงเวลา, partition, `workflow_process_date`)
   - ถ้าไม่เข้าทั้งสองเงื่อนไข **ข้ามข้อนี้ไปเลย** ไม่ต้องรบกวนผู้ใช้
   - **SQL ที่แทนค่าให้พร้อมรัน (อ่านอย่างเดียว ผมไม่รันเอง ให้รันด้วย user เดียวกับที่ ODI ใช้ต่อ):**
     ```sql
     SELECT product, version_full FROM product_component_version;
     SELECT DBTIMEZONE AS db_timezone, SESSIONTIMEZONE AS session_timezone,
            TO_CHAR(SYSDATE,'YYYY-MM-DD HH24:MI:SS') AS sysdate_value,
            TO_CHAR(SYSTIMESTAMP,'YYYY-MM-DD HH24:MI:SS TZR') AS systimestamp_value
     FROM dual;
     ```
   - **อ่านผล:** Oracle ต่ำกว่า 12.2 → หยุดและแจ้งก่อนแปลง (กฎ C9/D-R8 ใช้ไม่ได้) · `sysdate_value` ไม่ตรงกับ `spark.sql.session.timeZone` ที่ได้จากขั้น [S] → ถามผู้ใช้ก่อนปิด I10 (D-R9) อย่าสรุปจาก `DBTIMEZONE` อย่างเดียว เพราะไม่ได้กำหนด `SYSDATE`
   - ผู้ใช้เลือกข้ามได้ → บันทึก "ยังไม่ได้ตรวจเวอร์ชัน/timezone ของ Oracle" เป็นสมมติฐานที่ยังไม่ยืนยันใน `status/MIGRATION_STATUS.md` และรายงานปิดงาน

**ต้องสแกนเองก่อนถาม — สแกน 3 ชุด แล้วรายงานเป็นข้อๆ ว่าเจออะไรที่ไฟล์ไหน บรรทัดไหน**

**ชุดที่ 1 — Spark-ism (ไวยากรณ์/ฟังก์ชันที่ Oracle ไม่มี)**
`concat(` · `format_string(` · `left(` / `right(` · `nullif(x,'')` · `reverse(` · `split(` ·
`regexp_extract(` · `INSERT OVERWRITE` · `to_date(` แบบอาร์กิวเมนต์เดียว ·
`order by 1` ใน analytic function · `IFNULL(` · `TRY_CAST(` · `LIMIT n` · `CAST(x AS STRING/LONG/…)`

**ชุดที่ 2 — `INSERT` ที่ไม่มี column list**
หา `INSERT\s+INTO\s+\S+\s+SELECT` (คือหลังชื่อตารางไม่มีวงเล็บเปิด) ทุกจุด แล้ว**รายงานทุกตัว
พร้อมชื่อตารางปลายทาง** นี่คือ positional insert ซึ่งผูกกับลำดับคอลัมน์ของตาราง
Spark เขียน `INSERT OVERWRITE TABLE x SELECT …` แบบ positional โดยธรรมชาติ การแปลงตรงๆ
จึงได้ positional insert ออกมาเสมอถ้าไม่ตั้งใจแก้ **[เกิดขึ้นจริงมาแล้ว — ORA-00947 ตอนรันจริง
ดู `knowledge/lessons-learned.md` L24]**

**ชุดที่ 3 — ชื่อตารางที่ไม่ qualify**
เก็บชื่อตารางทุกตัวที่ตามหลัง `FROM` / `JOIN` / `INSERT INTO` / `MERGE INTO` /
`TRUNCATE TABLE` / `UPDATE` แล้วดูว่าตัวไหน**ไม่มีจุด** (ไม่นับ `DUAL`, alias และ inline view
ที่ตามด้วยวงเล็บ) — ต้องเติม schema ตามที่ตอบไว้ใน **I4** ระหว่างการแปลง
⚠️ คำว่า `FROM` ที่อยู่ใน `EXTRACT(… FROM x)` / `TRIM(… FROM x)` **ไม่ใช่การอ้างตาราง**
อย่านับรวม (เป็นบั๊กที่ตัวตรวจเองเคยทำ — `knowledge/lessons-learned.md` L35)

**ชุดที่ 4 — รูปร่างของ statement**
- **`INSERT` ที่ไม่ได้ขึ้นต้นด้วย `INSERT INTO`** — ประโยค `WHEN NOT MATCHED THEN INSERT`
  ข้างใน `MERGE` และทุกสาขาของ `INSERT ALL` ต้องมี column list เหมือนกัน กฎ D-R1 ไม่ได้
  ผูกกับคำว่า `INSERT INTO` **[`knowledge/lessons-learned.md` L24]**
- **`;` ปิดท้าย หรือมีหลาย statement ในไฟล์เดียว** — ODI ส่งข้อความเข้า JDBC ตรงๆ
  `;` จะกลายเป็น `ORA-00911` ตอนรัน ทั้งที่รันผ่านใน SQL Developer **[`knowledge/lessons-learned.md` L26]**
- **ไฟล์ `.sql` ที่ว่างหรือมีแต่คอมเมนต์** — จะได้ step ที่ import ผ่านแล้วไม่ทำอะไร
- **`TO_DATE` / `TO_NUMBER` / `TO_CHAR` ที่ไม่มี format mask** — ผลขึ้นกับ NLS ของ session
  ที่ ODI agent รัน ซึ่งไม่เหมือนกับ session ที่คนใช้เทส **[`knowledge/lessons-learned.md` L30]**

> ถ้ารัน python ได้ ชุดที่ 2, 3 และ 4 มีสคริปต์ตรวจให้แล้ว (ยกเว้น format mask ที่ต้องดูเอง):
> `python scripts/checks/check_sql.py <โฟลเดอร์ sql>` ทำงานโดยไม่ต้องต่อฐานข้อมูล
> ดู `README.md`

**ถ้ายังเป็น Spark:** แปลงตาม `knowledge/reference/spark-to-oracle-sql.md` ห้ามแปลแบบเฉพาะกิจกลางทาง — SQL ที่แปลงผิดจะ
import ผ่านเงียบๆ แล้วไปพังตอน runtime ซึ่ง debug ยากกว่ามาก

### [I11/17] สถาปัตยกรรม — Procedure, Mapping หรือ ผสม

**ถามว่า:**
> `[I11/17]` งานนี้จะทำเป็น ODI **Procedure**, **Mapping**, หรือ **ผสม** (บางทาสก์ Procedure
> บางทาสก์ Mapping) ครับ
> ผมแนะนำ **`<Procedure / ผสม — ระบุตามเกณฑ์ใน `migration-rules.md` หัวข้อ 5 และ knowledge/reference/optional/mapping-based-path.md F7>`** เพราะ
> `<เหตุผลจากงานนี้จริง>`
> ผลต่างที่ชัดที่สุด: ทาสก์ที่ทำเป็น Procedure ได้ XML ที่ import แล้วรันได้เลย ส่วนทาสก์
> ที่ทำเป็น Mapping ผมส่งได้แค่ build spec ให้คนไปสร้างใน Studio เอง (ยังไม่มีใครสร้าง Mapping
> XML ที่ import ผ่าน) — ODI ใส่ Procedure กับ Mapping ไว้ใน Package เดียวกันได้ปกติ ไม่ขัดกัน
> เอาแบบไหนครับ 1) Procedure ทั้งหมด 2) Mapping ทั้งหมด (เท่าที่เข้ารูปได้) 3) ผสม

**ตัวเลือกที่ 3: ผสม (มักเป็นทางเลือกที่เหมาะสุดในทางปฏิบัติ)**

แม้เลือกเส้นทาง Mapping ก็ไม่ใช่ทุกทาสก์ที่ควรเป็น Mapping (ดูเกณฑ์ตัดสินรายทาสก์ใน
`knowledge/reference/optional/mapping-based-path.md F7`) งานส่วนใหญ่ที่มี multi-statement (`TRUNCATE`+`INSERT`), correlated subquery,
window function หนักๆ, หรือเป็น control/status task **จะเหมาะเป็น Procedure อยู่ดี** ต่อให้
ภาพรวมเลือกเส้นทาง Mapping ส่วนที่เหลือซึ่งเป็น source→target ตรงๆ ค่อยทำเป็น Mapping —
**ต้องไล่เกณฑ์ F7 ทีละทาสก์แล้วเสนอเป็นตารางก่อนถาม** ไม่ใช่ถามลอยๆ ว่า "อยากผสมไหม"

**ต้องได้อะไรกลับมา**

1. **เลือกหนึ่งทาง** — Procedure (default), Mapping (ทุกทาสก์ที่เข้ารูปได้), หรือ ผสม
2. **ถ้ามีทาสก์ไหนจะเป็น Mapping (ไม่ว่าเลือกทางไหนใน 3 ทาง) ต้องยืนยันว่ารับทราบ 3 อย่าง**
   - ทาสก์เหล่านั้นไม่ได้ไฟล์ที่ import แล้วรันได้ ได้แค่ build spec + SQL ที่แปลงแล้ว
   - ต้อง reverse-engineer Datastore ของทุกตารางที่เกี่ยวข้องใน Studio ก่อน ถึงจะสร้าง Mapping ได้
   - เวลาที่ใช้อยู่ที่คน ประมาณจากจำนวน Mapping × เวลาต่อตัวของทีม
3. **ถ้ามีทาสก์ไหนจะเป็น Mapping ต้องถามต่อ** — ทีมมี Knowledge Module ที่ customize เองไหม
   ถ้ามีให้ใช้ของทีม อย่าเสนอ KM มาตรฐาน — **ถ้าทีมตอบไม่ได้ตอนนี้ ให้เสนอ KM มาตรฐานไปก่อน
   แล้วบันทึกเป็น open item ที่ต้องยืนยันกับทีมทีหลัง** (ห้ามค้างคาไม่ขยับต่อ)
   ⚠️ ไฟล์ reference จาก I2 **จะไม่มีข้อมูล KM ให้อ่านเลย** ถ้าตอน export ไม่ได้ทำสเปกข้อ 10
   (Mapping ตัวอย่าง) ไว้ในนั้น — เช็คก่อนด้วย `grep -i 'class="[^"]*Km[^"]*"\|class="[^"]*Map[^"]*"'`
   กับไฟล์ reference ถ้าไม่เจอเลย ต้องถามคนตรงๆ ห้ามเดาว่ามีหรือไม่มี
4. **ถามว่าทีมทำงานแบบไหนอยู่แล้ว** — package ที่ทีมใช้จริงตอนนี้เป็น Procedure, Mapping หรือผสม
   **คำตอบข้อนี้มีน้ำหนักมากกว่าคำแนะนำทั่วไป** การทำตามแบบที่ทีมใช้อยู่ทำให้คนรีวิวและ
   คนดูแลต่อทำงานได้ทันที

**ต้องหาเองก่อนถาม** — ไล่ทุกทาสก์ทีละตัวตามเกณฑ์ `knowledge/reference/optional/mapping-based-path.md F7` แล้วแสดงเป็นตาราง
(ทาสก์ / เหมาะเป็น Procedure หรือ Mapping / เหตุผล) ก่อนเสนอคำแนะนำภาพรวม อย่าสรุปลอยๆ
เช่น *"6 ใน 8 ทาสก์เป็น overwrite ที่ต้อง `TRUNCATE` ก่อน `INSERT` ซึ่งเป็นสอง statement —
ทำเป็น Mapping ต้องแยกเป็นสอง object อยู่ดี"*

**ผลถ้าตอบผิด** — เคยมีคนเลือก Mapping ทั้งชุดโดยไม่ได้ดูว่าทีมใช้อะไร แล้วเสียเวลาหลายสัปดาห์
กับ `SnpMapComp`/`SnpMapAttr` และจบที่ NullPointerException ใน Studio
(`knowledge/reference/delivery-checklist.md` ข้อ 10)

**อ่านต่อ** — ถ้ามีทาสก์ไหนจะเป็น Mapping (เลือก Mapping หรือ ผสม) ให้ไปที่
`knowledge/reference/optional/mapping-based-path.md` ทั้งไฟล์

### [I12/17] ทาสก์ที่ implement ตรงๆ ไม่ได้ (ต้องตัดสินใจเพิ่ม)

⚠️ **ห้ามให้ agent เสนอตัดเป็นค่าเริ่มต้น** — แนวทางเดิมให้ agent "เสนอตัด" เป็นค่าเริ่มต้น ซึ่งทำให้
ดูเหมือน agent ตัดสินใจแทนผู้ใช้เรื่อง business impact ที่ตัวเองมองไม่เห็น และเคยเปิดช่องให้
agent เสนอทางแก้ที่พึ่งพาการสร้าง object ใหม่ (เช่น "เดี๋ยว DBA สร้างตารางให้ทีหลัง") ซึ่งขัดกับ
ข้อห้ามเรื่อง DDL ของเอกสารนี้เอง **[เกิดขึ้นจริงมาแล้ว — ดูรายละเอียดในแต่ละจุดด้านล่าง]**
กฎใหม่: **agent รายงานข้อเท็จจริงทางเทคนิคเท่านั้น ไม่เสนอคำแนะนำว่าควรตัดอะไร แล้วให้ผู้ใช้
เป็นคนเลือกทางแก้ทีละทาสก์**

⚠️ **แก้เพิ่มใน v11 รอบ 2** — ผู้ใช้ชี้ว่าการห้ามเสนอ object ใหม่แบบเด็ดขาด (หัวข้อ 9) เข้มไป
เกินไป เพราะ agent ควรช่วยคิดไอเดียได้ ขอแค่คนเป็นคน approve ก่อนทุกครั้ง ไม่ใช่ agent ตัดสินใจ
แทนเงียบๆ — เพิ่ม **ตัวเลือกที่ 5** ในขั้นที่ 2 ด้านล่างสำหรับกรณีนี้โดยเฉพาะ (หลักการเดียวกับกฎ
การถามข้อ 11 ซึ่งใช้กับทุก Q ไม่ใช่แค่ I12)

**วิธีหา "ทาสก์ไม่มี SQL" ก่อนถาม (อย่าไล่เปิดดูทีละทาสก์เอง)** — เช็คสองจุดต่อทาสก์ตาม
`knowledge/reference/blendata-json-schema.md`:
1. มี key `body.aggregationConfig.sql` หรือ `body.sql` เป็น string ที่ไม่ว่างไหม — ถ้าไม่มีเลย = ไม่มี SQL
2. ดู `serviceTemplate` ประกอบ — `service-job-aggregate` มักมี SQL, ส่วน `service-job-recover` /
   `service-job-table-retention` (และชื่ออื่นที่ขึ้นต้น `service-job-` แต่ไม่ใช่ aggregate)
   มักเป็น infra-only ไม่มี SQL — **แต่ต้องยืนยันด้วยจุดที่ 1 เสมอ อย่าตัดสินจากชื่อ
   `serviceTemplate` อย่างเดียว** เพราะเป็น pattern ที่เห็นจากไฟล์จริงจำนวนจำกัด ไม่ใช่สเปกที่ยืนยันแล้ว **[เห็นในไฟล์จริง]**

สำหรับทาสก์ที่ sink ไม่ใช่ Oracle ให้เช็คเพิ่ม: มี connection นั้นอยู่ใน Topology ของไฟล์
reference ด้วยไหม (ตาม I16) — ถ้าไม่อยู่ ให้ถือว่า **ไม่มีทางทำให้ import แล้วรันได้จริง**
ในรอบนี้ ไม่ว่าจะเดา connection detail เองหรือฝัง credential ที่เห็นใน source material ก็ตาม
(ทั้งสองอย่างเป็นข้อห้ามเด็ดขาดอยู่แล้ว ดูข้อ 9)

**ขั้นที่ 1 — รายงานสถานะทุกทาสก์ก่อน (ยังไม่ใช่คำถาม)**

แสดงตารางทาสก์ทั้งหมด `<n>` ตัวจาก DAG ให้ผู้ใช้เห็นภาพรวมก่อน:

> จาก DAG ทั้งหมด `<n>` ทาสก์ แปลงตรงๆ ได้ `<k>` ตัว อีก `<m>` ตัว implement ตรงๆ ไม่ได้ด้วย
> ข้อมูลที่มีตอนนี้:
>
> | ทาสก์ | สถานะ | เหตุผล |
> |---|---|---|
> | `<task>` | ✅ แปลงได้ตรงๆ | — |
> | `<task>` | ⛔ ไม่มี SQL/config ในไฟล์ที่ได้รับ | ไม่มี ODI object เทียบเท่า |
> | `<task>` | ⛔ ปลายทางไม่ใช่ Oracle | ไม่มี connection `<ระบบ>` ใน Topology ของ reference |
>
> `<n> = <k> + <m>` (เช็คแล้วครบ) — ต่อไปจะถามทีละทาสก์สำหรับ `<m>` ตัวที่ ⛔ ว่าจะให้ทำอย่างไร

**ห้ามใช้คำว่า "ตัด" หรือ "แนะนำให้ตัด" ในขั้นนี้** — agent ไม่มีสิทธิ์รู้ business impact ที่แท้จริง
ของแต่ละทาสก์ ให้รายงานเป็นข้อเท็จจริงทางเทคนิคล้วนๆ เท่านั้น

**เช็คเลขให้ตรงก่อนแสดงตารางนี้ — บังคับ** `<k> + <m>` ต้องเท่ากับ `<n>` พอดีก่อนพิมพ์ออกไป
ถ้านับแล้วไม่ลงตัว แปลว่ามีทาสก์หายไปจากทั้งสองฝั่ง ต้องหาให้เจอว่าตกหล่นตัวไหนก่อน **ห้ามเสนอ
ตัวเลขที่ยังไม่ reconcile ให้ผู้ใช้เห็น** **[เกิดขึ้นจริงมาแล้ว — เคยนับทาสก์ตกหล่นไป 1 ตัวจนเกือบ
หลุดจาก step chain]**

**ขั้นที่ 2 — ถามทีละทาสก์สำหรับตัวที่ ⛔ (ตามกฎข้อ 9: หนึ่งคำถาม = หนึ่งทาสก์)**

**ถามว่า (ต่อทาสก์หนึ่งคำถาม):**
> `[I12.<i>/17]` ทาสก์ `<task>` implement ตรงๆ ไม่ได้ตอนนี้ — เหตุผล: `<เหตุผลจากตารางข้างบน>`
>
> ต้องการให้ทำอย่างไร?
> 1) สร้างเป็น placeholder (no-op procedure, ปลอดภัย ไม่กระทบข้อมูล) — เก็บเป็น open item
>    รอข้อมูลเพิ่มเติมในอนาคต
> 2) Redirect ไปยัง object ที่**มีอยู่แล้วจริง**และคุณยืนยันแล้วว่ามีจริง (ระบุชื่อ object) —
>    *ตัวเลือกนี้ใช้ได้เฉพาะเมื่อมี object จริงรองรับเท่านั้น ถ้าไม่มีให้ข้ามไปทางอื่น*
> 3) ให้ข้อมูลเพิ่มเติมตอนนี้เลย (เช่น connection จริงที่จะไปตั้งใน Topology, ปลายทางจริงอีกตัว)
>    แล้วให้ผมลองแปลงใหม่ให้เต็มรูปแบบ
> 4) สร้างเป็น placeholder เหมือนข้อ 1 แต่ยืนยันว่าจะไม่ implement ทาสก์นี้เลยในระยะยาว
>    (บันทึกเป็นช่องว่างที่ยอมรับแล้ว ไม่ใช่ open item ที่รอทำต่อ)
> 5) **เสนอให้สร้าง object ใหม่ในฐานข้อมูล** (เช่น ตารางหรือ connection ที่ยังไม่มี) — agent
>    บันทึกไอเดียนี้เป็นข้อเสนอ **รอคุณอนุมัติ**เท่านั้น ไม่ implement ทันที รอบนี้ยังคงสร้างเป็น
>    placeholder ไปก่อน (เหมือนข้อ 1) แล้วค่อยย้อนกลับมาที่ I12 ใหม่เพื่อ redirect จริง (ข้อ 2)
>    เมื่อมีคนสร้าง object นั้นจริงและยืนยันแล้วเท่านั้น *ใหม่ใน v11 รอบ 2*

**ต้องได้อะไรกลับมาต่อทาสก์**

1. **เลือกได้แค่ 1 ใน 5 ข้อข้างบนต่อทาสก์หนึ่งตัว** * (เดิม 1 ใน 4)* —
   ถ้าผู้ใช้บอกว่า "ใช้แบบเดียวกันทุกตัว" ต้องย้อนยืนยันแบบเจาะจงชื่อทาสก์ทุกตัวที่จะใช้คำตอบนั้น
   ก่อน ไม่ใช่รับคำตอบสั้นๆ แล้วเหมาเอาเอง
2. **ข้อ 2 (redirect) ห้ามเสนอหรือรับถ้าไม่มี object จริงรองรับ** ไม่ว่าจะระบุว่า "ให้ DBA สร้าง
   ให้ทีหลัง" หรือ "สร้างเองตอน deploy" ก็ตาม — **การพึ่งพาการสร้าง object ใหม่ (`CREATE TABLE`,
   เพิ่ม connection ใหม่ที่ต้องเดา credential) ไม่ว่าจะระบุว่าใครเป็นคนทำ ถือว่าอยู่นอกขอบเขตของ
   ทางเลือกนี้เสมอ** — ถ้าไม่มี object จริงรองรับ ต้องตกไปที่ข้อ 1, 3, 4 หรือ 5 เท่านั้น
   **[เกิดขึ้นจริงมาแล้ว — เคยเสนอ redirect ทาสก์ export ไป SQL Server ให้ไปเขียนตาราง Oracle
   ใหม่ที่ยังไม่มีอยู่จริงแทน โดยไม่ทันสังเกตว่าเท่ากับสมมติว่าจะมีคนรัน `CREATE TABLE` ให้ ต้อง
   ย้อนกลับมาแก้เป็น placeholder ทีหลัง]**
3. **ข้อ 5 (เสนอ object ใหม่) ต่างจากข้อ 2 ตรงที่ยังไม่มี object จริงรองรับ ณ ตอนนี้** —
   deliverable ของรอบนี้ยังคงเป็น placeholder เสมอ (เหมือนข้อ 1) ไม่ใช่ `INSERT` ไปยังตารางที่
   ยังไม่มีอยู่จริง ไอเดียที่เสนอต้องบันทึกเป็น open item ในรายงานปิดงาน พร้อมระบุว่า "รอผู้ใช้
   อนุมัติ + รอคนสร้าง object จริง" — เมื่อมีทั้งสองอย่างแล้วค่อยย้อนกลับมาที่ I12 ใหม่เพื่อเปลี่ยน
   เป็นข้อ 2 (redirect จริง) ในรอบถัดไป **agent ห้ามข้ามขั้นตอนอนุมัตินี้เอง ไม่ว่าจะดูเป็นไอเดีย
   ที่ดีแค่ไหน** *(ตอบ feedback ที่ว่าการห้ามเสนอไอเดียเลยเข้มไป*
4. **ทั้งข้อ 1 และข้อ 4 ต้องได้ object ODI จริงเสมอ (placeholder Procedure)** ไม่ใช่การไม่มี object
   ใดๆ เลยสำหรับทาสก์นั้น — ต่างกันแค่วิธีบันทึกในรายงานปิดงาน (ข้อ 1 = "รอข้อมูลเพิ่มเติม",
   ข้อ 4 = "ยอมรับเป็นช่องว่างถาวรแล้ว") ทาสก์ทุกตัวจาก DAG **ต้องปรากฏใน step chain ของ output
   เสมอ ไม่ว่าจะเลือกข้อไหนก็ตาม** (ดู `knowledge/reference/delivery-checklist.md` ข้อใหม่เรื่องนี้)
5. **ยืนยันผลกระทบแบบเจาะจง ไม่ใช่พูดกว้างๆ ว่า "pipeline ไม่ครบ"** — บอกตรงๆ ว่าตารางหรือ
   ขั้นตอนไหนจะไม่ถูกทำอัตโนมัติ (เช่น "ตาราง staging จะไม่ถูกเคลียร์ให้อัตโนมัติ ต้องมีคนหรือ
   job อื่นมาทำแทน" ไม่ใช่แค่ "กระทบ business logic")
6. **ห้าม AI แต่ง logic ทดแทนขึ้นเองเด็ดขาด** ไม่ว่าจะเลือกข้อไหนก็ตาม (เช่น เดาว่าเป็น cleanup
   แล้วเขียน `TRUNCATE` ให้เอง) ไม่ว่าจะดูสมเหตุสมผลแค่ไหน — ถ้าผู้ใช้อยากได้ logic ทดแทนจริงๆ
   ต้องเป็นคนให้ SQL หรือบอก logic มาเองที่ข้อ 3 ไม่ใช่ AI เสนอเข้าไปก่อน **[เกิดขึ้นจริงมาแล้ว —
   เคยต้องบอกซ้ำหลายรอบกว่าจะได้ข้อสรุปนี้]**

7. **Placeholder Procedure (ข้อ 1 และข้อ 4) ต้อง embed comment block ที่มี logic/config เดิมจาก
   Blendata เต็มๆ เสมอ ไม่ใช่แค่ no-op เปล่าๆ** — โครงสร้างบังคับของ comment:
   - อธิบายว่าทาสก์นี้ทำหน้าที่อะไรเดิมใน Blendata (สรุปจาก `serviceTemplate` / `taskUrl` / `body` จริง)
   - แปะ config หรือ SQL เดิมของทาสก์นั้นแบบ verbatim จากไฟล์ export (ห้ามตีความหรือแต่งใหม่ —
     ขัดกับข้อ 6 ด้านบน) ยกเว้นฟิลด์ที่เป็น credential ต้อง redact ทิ้งเสมอตามข้อห้ามใน `migration-rules.md` หัวข้อ 7
   - อธิบายเหตุผลที่แปลงตรงๆ เป็น ODI ไม่ได้ (อ้างอิงเหตุผลจากตารางขั้นที่ 1)
   - คำสั่งจริงที่รัน (นอก comment) ยังคงเป็น no-op ปลอดภัยเหมือนเดิมเสมอ — **ห้ามให้การมี comment
     กลายเป็นข้ออ้างในการลองเดา logic ทดแทนขึ้นเอง** ข้อ 6 ยังใช้เต็มที่

   *ใหม่ใน v13 รอบ 2 — ผู้ใช้กำหนดให้ใช้เป็นค่าเริ่มต้นของทุกทาสก์ที่ตกลงเลือกข้อ 1 หรือ 4 ไม่ต้อง
   ถามซ้ำทุกครั้งว่าจะ comment แบบไหน แต่ยังต้องย้อนยืนยันชื่อทาสก์ทุกตัวที่จะใช้ค่าเริ่มต้นนี้ตามข้อ 1*

**ทุกทางเลือกข้างบนเป็นการตัดสินใจทางธุรกิจ ไม่ใช่เทคนิค — agent ห้ามเสนอว่าทางไหน "แนะนำ"
หรือ "ควรเลือก" เพราะ business impact อยู่นอกเหนือสิ่งที่ agent มองเห็นได้จากไฟล์ export**

### [I13/17] ลำดับ step chain ที่ flatten แล้ว

**ถามว่า:**
> `[I13/17]` DAG เดิมมีทาสก์ที่รันขนานกัน แต่ ODI Package ต่อ step ได้เป็นเส้นตรงเท่านั้น
> ผมบีบเป็นลำดับนี้: `<แสดงลำดับทั้งหมดพร้อม level และ parentTask เดิม>`
> จุดที่เดิมขนานกันคือ `<...>` ผมเรียงเป็น `<...>`
> ลำดับนี้โอเคไหมครับ

**ต้องได้อะไรกลับมา**

1. **ยืนยันลำดับทั้งเส้น** — ต้องแสดงตารางเทียบให้เห็น: ทาสก์ / `level` เดิม / `parentTask` เดิม / ลำดับใหม่
2. **ชี้จุดที่ DAG เป็น fan-out / fan-in ให้ชัด** และบอกผลกระทบตรงๆ ว่าทาสก์ที่เดิมรันขนานกันจะกลายเป็นรันเรียงกัน — ช้าลง แต่ผลลัพธ์เหมือนเดิมถ้าไม่มี dependency ข้ามกัน
3. **ถามว่าในกลุ่มที่เดิมขนานกัน ต้องเรียงตามลำดับไหนเป็นพิเศษไหม** หรือสลับได้
4. **ถ้ามี fan-in** ต้องยืนยันว่าทาสก์นั้นถูกวางไว้หลังทุกตัวที่มันรออยู่จริง

**ต้องทำเองก่อนถาม — cross-check ตารางกับลำดับ**

ไล่ SQL ทุกทาสก์ แยกเป็น "ตารางที่เขียน" (`INSERT INTO` / `MERGE INTO` / `TRUNCATE TABLE` /
`UPDATE`) กับ "ตารางที่อ่าน" (`FROM` / `JOIN`) แล้วหาจุดที่ **step หนึ่งอ่านตารางที่ step
ถัดไปเพิ่งเขียน** เอามาแสดงให้ผู้ใช้ยืนยัน

⚠️ **ห้ามรายงานว่าเป็นข้อผิดพลาด** — ในงานจริงที่ทดสอบมาเจอแบบนี้ 4 จุดและถูกต้องทั้งหมด
เพราะเป็นแพตเทิร์น checkpoint/watermark ปกติ (อ่านค่าของรอบก่อน เขียนค่าของรอบใหม่ตอนท้าย)
ให้ถามว่า *"จุดเหล่านี้ตั้งใจให้อ่านข้อมูลของรอบก่อนใช่ไหมครับ หรือเป็นลำดับที่ผม flatten ผิด"*

นี่คือเหตุผลที่เช็คนี้อยู่ในขั้นถามตอบ ไม่ได้อยู่ในตัวตรวจไฟล์ — ถ้าทำเป็นกฎอัตโนมัติ
มันจะฟ้องงานที่ถูกต้อง

### [I14/17] overwrite / append / upsert รายทาสก์ + column list ของทุก `INSERT`

⚠️ **แก้ไขใน v11 — เดิมคำถามนี้รวมทั้งตารางภาพรวมและการตัดสินใจย่อยหลายเรื่อง (แถว ⛔/🔶/⚠️)
ไว้ในข้อความเดียว ทำให้ผู้ใช้ตอบสั้นๆ มาแบบไม่ชัดว่าหมายถึงแถวไหน ต้องย้อนถามซ้ำหลายรอบ
[เกิดขึ้นจริงมาแล้ว] ตอนนี้แยกเป็น: (1) แสดงตารางภาพรวมเพื่อขอคำยืนยันเฉยๆ (2) ถามทีละแถวที่
ต้องตัดสินใจ ด้วยตัวเลือกเลขเสมอ ตามกฎข้อ 9–10**

**ขั้นที่ 1 — ถามว่า (ยืนยันตารางภาพรวมอย่างเดียว):**
> `[I14/17]` ผมอ่าน `sinkOption.mode` กับ `sinkOption.partitions` จาก DAG มาแล้ว และเทียบ
> column list ของทุก `INSERT` กับตารางปลายทางให้แล้ว — ตารางนี้ครับ
>
> | ทาสก์ | mode | `partitions` เดิม | ตารางปลายทาง (+schema จาก I4) | คำสั่งที่จะสร้าง | column list | ที่มาของ column list |
> |---|---|---|---|---|---|---|
> | `<task>` | overwrite | *(ว่าง)* | `<schema>.<table>` | `TRUNCATE` + `INSERT` | ✅ มี (28/28) | DDL จริง |
> | `<task>` | overwrite | `<partition key>` | `<schema>.<table>` | ⛔ **ต้องเลือกก่อน (ถามแยกด้านล่าง)** | ✅ มี (28/28) | DDL จริง |
> | `<task>` | append | — | `<schema>.<table>` | `INSERT` บรรทัดเดียว | ✅ มี (28/28) | 🔶 **เดา — ยังไม่ยืนยัน (ถามแยกด้านล่าง)** |
> | `<task>` | upsert | — | `<schema>.<table>` | `MERGE` บรรทัดเดียว | ✅ มี (28/28) | DDL จริง |
> | `<task>` | append | — | `<schema>.<table>` | `INSERT` บรรทัดเดียว | ⚠️ **ยังไม่ตัดสินใจ (ถามแยกด้านล่าง)** | — |
>
> ตารางนี้ถูกต้องไหมครับ (mode / column list / ที่มาของ column list) — แถวที่มีเครื่องหมาย
> ⛔ 🔶 ⚠️ จะถามแยกเป็นคำถามต่อไปทีละแถวครับ

**ขั้นที่ 2 — ถามแยกทีละแถวที่ต้องตัดสินใจ (หนึ่งคำถาม = หนึ่งแถว/หนึ่งทาสก์ ตามกฎข้อ 9)**

สำหรับแถว **⛔** แต่ละแถว (ถ้ามีหลายทาสก์ที่เป็น ⛔ ต้องถามแยกทีละทาสก์ ห้ามรวม):
> `[I14.⛔<i>/17]` ทาสก์ `<task>`: งานเดิมเขียนทับเฉพาะ partition ที่ระบุ (`<partition key>`)
> ไม่ใช่ทั้งตาราง ถ้าแปลงเป็น `TRUNCATE TABLE` ตรงๆ **ข้อมูลของ partition อื่นทั้งหมดจะหายถาวร**
> เลือกได้:
> 1) `DELETE FROM <ตาราง> WHERE <partition key> = <ค่าของรอบนี้>` แล้วค่อย `INSERT`
>    (ตรงกับพฤติกรรมเดิมที่สุด ช้ากว่า กิน undo มากกว่า — รูปแบบมาตรฐานและการยืนยัน `partitionOverwriteMode` ดู `knowledge/reference/spark-to-oracle-sql.md` หัวข้อ "overwrite เฉพาะ partition")
> 2) `ALTER TABLE <ตาราง> TRUNCATE PARTITION <ชื่อ>` ถ้าตารางฝั่ง Oracle partition
>    ด้วยคีย์เดียวกันจริง (เร็วที่สุด แต่ต้องให้ DBA ยืนยันชื่อ partition)
> 3) ยืนยันว่าตั้งใจให้เขียนทับทั้งตารางจริงๆ (ตารางปลายทางเก็บแค่รอบล่าสุด)

สำหรับแถว **🔶** แต่ละแถว:
> `[I14.🔶<i>/17]` ทาสก์ `<task>`: column list ของตาราง `<table>` มาจากการเดา ยังไม่ยืนยัน
> เลือกได้:
> 1) ยอมรับความเสี่ยง ใช้ column list ที่เดาไว้ต่อไป (จะติด flag ในรายงานปิดงานเสมอ)
> 2) หยุดรอ — ขอ DDL จริงของตารางนี้ก่อนไปต่อ

สำหรับแถว **⚠️** แต่ละแถว:
> `[I14.⚠️<i>/17]` ทาสก์ `<task>`: column list ของตาราง `<table>` ยังไม่ได้ตัดสินใจว่าจะรอ DDL
> หรือจะเดา เลือกได้:
> 1) รอ DDL จริงก่อนไปต่อ
> 2) เดาจาก SELECT list ของ Blendata ไปก่อน (ยอมรับความเสี่ยง จะติด flag ในรายงานปิดงานเสมอ)

**ต้องได้อะไรกลับมา**

1. **ยืนยัน mode ของทุกทาสก์** แสดงเป็นตาราง task → mode ที่อ่านได้ → คำสั่งที่จะสร้าง
   (ไม่ต้องถามเรื่องเลข `OrdTrt` หรือ `SqlIndGrp` — สองค่านี้อ่านจาก reference และจากตำแหน่งบรรทัด ดู `knowledge/reference/odi-object-reference.md`)
2. **ยืนยันว่าทุก `INSERT` มี column list ครบแล้ว**
   - ตารางข้างบนต้องมีคอลัมน์ **column list** ทุกแถว และต้องเป็น ✅ ทั้งหมดก่อนไปต่อ (มาจาก DDL จริง
     หรือมาจากโหมดเดาที่ยืนยันแล้วที่ I3 ก็นับเป็น ✅ ได้ — แค่ต้องติด flag ที่มาให้เห็นชัด)
   - แถวไหนยังเป็น ⚠️ **"ยังไม่ตัดสินใจ"** แปลว่ายังไม่ได้เลือกที่ I3 ว่าจะรอ DDL หรือจะเดา —
     ต้องให้ผู้ใช้เลือกทางใดทางหนึ่งตรงนี้ก่อนไปต่อ **ห้ามเดาชื่อคอลัมน์เองแบบไม่ประกาศ** (คือเดาได้
     แต่ต้องเป็นการเดาที่ผู้ใช้รับทราบและยืนยันแล้วเท่านั้น) **[เกิดขึ้นจริงมาแล้ว — ดู `knowledge/lessons-learned.md` L24]**
   - **ห้ามปล่อยให้ `INSERT` ไม่มี column list ผ่านไปโดยบอกว่า "เดี๋ยวไปเจอตอนรัน"** —
     ถ้าจำนวนคอลัมน์ไม่ตรงจะได้ `ORA-00947` / `ORA-00913` ตอนรัน แต่ถ้า**จำนวนตรงแต่ลำดับต่าง**
     จะรันผ่านแล้วเขียนข้อมูลลงผิดคอลัมน์โดยไม่มี error เลย **[เกิดขึ้นจริงมาแล้ว — ดู `knowledge/lessons-learned.md` L24]**
   - แถวที่เป็น 🔶 (เดา) ต้องถูกยกไปลงรายการใน "สิ่งที่ส่งมอบ" (`deliverables.md` หัวข้อ 1) แบบระบุชื่อตารางชัดเจน
     เสมอ ไม่ว่าผู้ใช้จะยืนยันกี่รอบก็ตาม
3. **ยืนยันว่าชื่อตารางทุกตัว qualify ด้วย schema จาก I4 แล้ว** — ทั้งตารางปลายทางและตารางที่อ่าน
4. **ถ้าเจอ mode ที่ไม่รู้จัก** ต้องถามว่าจะให้แปลเป็นอะไร ห้ามเดา
5. **ต้องเตือนเรื่อง TRUNCATE** — `TRUNCATE` เป็น DDL ใน Oracle จะ commit ทันทีและ rollback ไม่ได้ ถ้าอยากให้อยู่ใน transaction เดียวกันและ rollback ได้ ต้องใช้ `DELETE FROM` แทน (ช้ากว่า) — ให้ผู้ใช้เลือก
   - ⚠️ ถ้าเลือก `DELETE` ต้องถามค่า `SqlIndGrp` ของบรรทัดนั้นด้วย เพราะค่านี้อ่านจากชนิดคำสั่งที่**มีอยู่จริงในไฟล์ reference** เท่านั้น คำสั่งที่ reference ไม่มีตัวอย่าง (`DELETE`, `WITH`, `BEGIN`, statement ที่ขึ้นต้นด้วยวงเล็บ) ต้องให้คนระบุ — ห้ามเดา
6. **ถ้าทาสก์เขียนลงตารางเดียวกันหลายตัว** ต้องยืนยันว่าตัวที่ truncate ต้องรันก่อนตัวที่ append ไม่ใช่สลับกัน
7. **ทาสก์ overwrite ทุกตัว ต้องอ่าน `sinkOption.partitions` ก่อนเสมอ**
   - **ว่าง** → แปลงเป็น `TRUNCATE TABLE` + `INSERT` ตามปกติ
   - **ไม่ว่าง** → **ห้ามแปลงเป็น `TRUNCATE TABLE` เอง** ต้องให้ผู้ใช้เลือกหนึ่งในสามทางในคำถาม
     `[I14.⛔<i>/17]` แยกทีละทาสก์ (ขั้นที่ 2 ข้างบน) แล้วบันทึกคำตอบลงรายงานปิดงานแบบระบุชื่อตารางเป็นรายใบ
     นี่คือความพังที่**ย้อนกลับไม่ได้**และ**ไม่มี error ฟ้อง** — `TRUNCATE` เป็น DDL ที่ commit
     ทันที และการตรวจนับแถวใน `knowledge/reference/validation-and-cutover.md` ระดับ 1 จะผ่านถ้าเทียบเฉพาะ partition ของรอบนี้
     **[`knowledge/lessons-learned.md` L29 · `delivery-checklist.md` ข้อ 41]**
   - ถ้า DAG ไม่มี field `partitions` เลย ให้ถามผู้ใช้ตรงๆ ว่างานเดิมเขียนทับทั้งตารางหรือเฉพาะ
     บางช่วง **ห้ามเหมาว่าทั้งตาราง**
   - **บันทึกผลของทุกทาสก์ overwrite (ทั้งว่างและไม่ว่าง) ลงไฟล์ `partitions_check.csv` ทันที
     ที่ได้คำตอบแต่ละแถว** — คอลัมน์ `TABLE_NAME,PARTITIONS_EMPTY`
     (`Y` = ว่าง ยืนยันว่า `TRUNCATE` ทั้งตารางถูกต้อง, `N` = ไม่ว่าง) หนึ่งแถวต่อหนึ่งตารางปลายทาง
     ชื่อตารางใช้ตัวเดียวกับที่ qualify แล้วจาก I4 — ไฟล์นี้คือสิ่งที่ปลดล็อกให้
     `check_sql.py --partitions` (ดู `migration-rules.md` หัวข้อ 6) ตรวจ D-R7 ได้จริงเป็น `[ERROR]`/`[OK]` แทนที่จะได้
     แค่ `[WARN]` ทั่วไปตลอดทุกครั้ง **ถ้าไม่สร้างไฟล์นี้ไว้ L29 จะยังไม่มี automated
     backstop เลยตอน build จริง ต้องพึ่งการถาม-ตอบใน `[I14.⛔<i>/17]` ล้วนๆ เหมือนก่อน v16**
   - **ถ้ารัน python ได้ ให้รัน `python scripts/checks/extract_partitions.py <DAG JSON จาก I1> -o
     partitions_check.csv` ก่อนลงมือพิมพ์เอง** — สคริปต์อ่าน
     `sinkOption.partitions` จาก DAG JSON ตัวเดียวกับที่ใช้ตอบ I1 แล้วสร้าง `partitions_check.csv`
     ให้อัตโนมัติสำหรับทุกตารางที่ field `partitions` มีอยู่จริง (ทั้งว่างและไม่ว่าง) เหลือแค่
     ทาสก์ที่ field หายไปทั้ง field หรือตารางเดียวกันถูกเขียนทับจากหลายทาสก์ด้วยผลขัดกัน ที่สคริปต์จะ
     แยกพิมพ์เป็นรายการ "ต้องถามผู้ใช้" ตรงๆ ตามกฎข้อนี้เอง ไม่ใส่ลง CSV ให้เดาเอง — ถามแล้วเติมแถวนั้น
     เองด้วยมือ (ใส่ `user-confirmed` ในคอลัมน์ `SOURCE` แทน `auto-from-dag`) **ถ้ารัน python ไม่ได้
     ให้พิมพ์ไฟล์เองทั้งหมดตามรูปแบบข้างบน** (ดู `README.md` หัวข้อ
     `extract_partitions.py`)
   - **(v18) คำตอบ I14 ของแถวที่ `PARTITIONS_EMPTY=N` ต้องกรอกในคอลัมน์ `DECISION` ของ `partitions_check.csv`
     โดยคนเป็นผู้ตัดสินใจ — สคริปต์ไม่เลือกให้** ค่าที่ใช้ได้: `delete_by_partition` (DELETE เฉพาะ partition ที่
     SELECT จะผลิต แล้ว INSERT [แนะนำ]) หรือ `truncate_all` (ล้างทั้งตาราง ต้องมีเหตุผลรองรับ) ว่างไว้ = `gen_dml.py`
     หยุดและไม่เขียนไฟล์ใด ๆ คอลัมน์ `PARTITION_COLUMNS` ถูกเติมจาก DAG อัตโนมัติ และรัน `extract_partitions.py`
     ซ้ำจะไม่ทับ `DECISION` ที่กรอกไว้แล้ว
8. **ทาสก์ upsert ที่จะเป็น `MERGE`** ต้องได้สองอย่างเพิ่ม
   - **column list ของประโยค `INSERT` ข้างใน `MERGE`** — กฎ D-R1 ใช้กับรูปนี้ด้วย
     `WHEN NOT MATCHED THEN INSERT VALUES (…)` แบบไม่มีวงเล็บชื่อคอลัมน์ คือความพัง
     ตัวเดียวกับL24 **[`knowledge/lessons-learned.md` L24 · `delivery-checklist.md` ข้อ 36]**
   - **ยืนยันว่า subquery ใน `USING` คืนหนึ่งแถวต่อหนึ่งคีย์** ไม่งั้นได้ `ORA-30926` ตอนรัน
     ให้ส่ง query นับคีย์ซ้ำใน `knowledge/lessons-learned.md` L31 ให้ผู้ใช้ไปรันเอง (SELECT ล้วน)
     **ถ้าต้องเติม dedup ห้ามเลือกเองว่าแถวไหนชนะ** — เป็น business logic ต้องถาม

**ต้องทำเองก่อนถาม** — ไล่ทุก `INSERT` (รวมที่อยู่ใน `MERGE` และ `INSERT ALL`) แล้วเติม
คอลัมน์ของตารางให้ครบ ถ้ารัน python ได้ ใช้ `python scripts/checks/check_sql.py <โฟลเดอร์ sql>`
ซึ่งนับให้โดยไม่ต้องต่อฐานข้อมูล (ตัวเลข "คอลัมน์ของตาราง" ยังต้องมาจาก DDL ที่ผู้ใช้ให้ —
สคริปต์ตรวจแค่ว่ามี column list ไหม และจำนวนในลิสต์ตรงกับจำนวน expression ที่ส่งมาไหม)
และอ่าน `sinkOption.partitions` ของทุกทาสก์ overwrite จาก DAG JSON ตาม `knowledge/reference/blendata-json-schema.md`

> ตอนนี้ทีมมี logic จริงแล้วหรือยังครับ ถ้ามีขอ SQL / ชื่อตาราง control
> ถ้ายังไม่มี ผมจะทำตาม placeholder เดิมแล้วบันทึกเป็นข้อค้าง

**ต้องได้อะไรกลับมา**

1. **สถานะปัจจุบันของ logic นี้** — ยัง placeholder หรือมีของจริงแล้ว
2. **ถ้ามีของจริง:** ขอ SQL, ชื่อตาราง control, และคอลัมน์ที่ต้องเขียน
3. **ถ้ายังไม่มี:** ยืนยันว่าจะคัดลอก placeholder เดิมมาตรงๆ **ห้ามคิด logic ให้เอง** และต้องบันทึกเป็น open item ในรายงานตอนส่งมอบ
4. **ต้องบอกผลกระทบให้ชัด** — placeholder แปลว่า package จะไม่รู้ว่ารอบก่อนสำเร็จหรือไม่ ถ้ารันซ้ำอาจประมวลผลข้อมูลเดิมซ้ำ

**หาเองก่อนถาม:** อ่าน SQL ของ Variable ทุกตัวใน reference มาแสดงให้เห็น

### [I16/17] สภาพ repository ปลายทาง

**ถามว่า:**
> `[I16/17]` repository ที่จะ import เข้าไป เป็นแบบไหนครับ
> 1) repo เดียวกับที่ export ไฟล์ reference มา
> 2) repo อื่น ที่มี connection ชื่อเดียวกันแต่สร้างแยกกัน
> 3) repo ใหม่ ยังไม่มี topology อะไรเลย

**ต้องได้อะไรกลับมา** — คำตอบ 1 ใน 3 ข้อ และต้องอธิบายผลของแต่ละแบบ

1. **ข้อ 1 repo เดียวกัน** → ตอน import จะเห็น topology เป็น matched/update ปกติ ทำต่อได้เลย
2. **ข้อ 2 repo อื่นที่มี connection ชื่อเดียวกัน** → ⚠️ **อันตราย** GlobalId ไม่ตรงกัน จะได้ connection ซ้อนขึ้นมาอีกตัวหรือชนกันเรื่องชื่อ **ต้องกลับไป export reference จาก repo นั้นแทน** (กลับไป I2)
3. **ข้อ 3 repo ใหม่** → topology จะถูกสร้างใหม่ให้จาก object ที่ฝังในไฟล์ ทำต่อได้ แต่ต้องเตือนว่าหลัง import ต้องไปแก้ JDBC URL กับ user/password ใน Topology เองก่อนรัน เพราะ export ไม่มี password มาด้วย

**ทำไมต้องถาม:** นี่คือคำถามที่ป้องกัน `ODI-10113 Broken Link` และการสร้าง topology ซ้อน
ซึ่งเคยเกิดจริงทั้งสองแบบ **[พิสูจน์แล้ว]** และ AI มองไม่เห็น repository — ต้องให้คนบอก

### [I17b] error log (`LOG ERRORS`) — ตัวเลือก ไม่นับเป็น Q

**ทำไมถามแยก** — ตัวเลือกนี้ทำให้งานไม่ล้มเมื่อมีแถวเสีย แต่ต้องมีตาราง `ERR_<table>` ในฐานข้อมูลก่อน (เป็นการสร้าง object ใหม่ จึงตกอยู่ใต้ข้อห้ามใน `migration-rules.md` หัวข้อ 7) และ
ทำให้แถวที่เสียหายไปเงียบๆ ได้ถ้าไม่ตรวจ (`knowledge/lessons-learned.md` L32) **default = ปิด** — ถ้าไม่มีความต้องการติดตามแถวเสียโดยเฉพาะ ไม่ต้องเปิด

**ถามว่า:** (ถามหลังตอบ I17 แล้ว เป็นข้อความแยก)
> `[I17b]` ต้องการให้ INSERT/MERGE บันทึกแถวที่ error ลงตาราง error log (`LOG ERRORS`) ไหมครับ
> ถ้าเปิด: งานไม่ล้มเมื่อมีแถวเสีย แต่ต้องมีตาราง `ERR_<table>` ครบทุกตาราง และต้องตรวจจำนวนแถวใน `ERR_` ทุกครั้งหลังรัน
> 1) ปิด (แนะนำ — default)
> 2) เปิด

**ต้องได้อะไรกลับมา**

1. **ข้อ 1 ปิด** → ไม่ใส่ `LOG ERRORS` ใน SQL เลย บันทึกลง `status/MIGRATION_STATUS.md` จบ
2. **ข้อ 2 เปิด** → ห้ามใส่ `LOG ERRORS` ลง SQL ทันที ต้องทำตามลำดับ:
   (ก) เสนอสคริปต์ `error-log-setup.sql` ที่เรียก `DBMS_ERRLOG.CREATE_ERROR_LOG` ให้ทุกตารางปลายทาง (แทนค่าชื่อ schema/ตารางให้ครบ) พร้อมระบุว่า **นี่คือข้อเสนอ รอคุณอนุมัติและรันเอง** (กฎการถามข้อ 11)
   (ข) ถามผู้ใช้ว่ารันแล้วและตาราง `ERR_` ครบทุกตัวหรือยัง — ถ้าตอบว่ายัง **ถือว่าเลือกข้อ 1 ไปก่อน** ห้ามใส่ `LOG ERRORS` ใน SQL (ข้อห้ามใน `migration-rules.md` หัวข้อ 7)
   (ค) เมื่อผู้ใช้ยืนยันว่าครบ ค่อยใส่ `LOG ERRORS INTO <schema>.ERR_<table> ('<tag>') REJECT LIMIT UNLIMITED` ท้ายทุก DML และเพิ่มข้อ L6 ใน `output/validation/`
   (ง) ผู้ใช้ต้องมีสิทธิ์สร้างตารางใน schema นั้น — ถ้าไม่มี ให้ส่งสคริปต์ให้ DBA แทน (ไม่ใช่เหตุให้เดาว่ามีตารางแล้ว)
       ตรวจสิทธิ์ล่วงหน้าได้ด้วย (อ่านอย่างเดียว ให้ผู้ใช้รันด้วย user เดียวกับที่ ODI ใช้ต่อ ผมไม่รันเอง): `SELECT privilege FROM session_privs WHERE privilege IN ('CREATE TABLE','CREATE ANY TABLE')` —
3. บันทึกคำตอบและสถานะ (เสนอ/อนุมัติ/ยืนยันว่ามีตารางแล้ว) ลง `status/MIGRATION_STATUS.md` แยกเป็นบรรทัดตามลำดับเวลา
