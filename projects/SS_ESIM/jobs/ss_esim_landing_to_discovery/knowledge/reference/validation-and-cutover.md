> **อ่านตอนไหน** — ก่อนตรวจตัวเลข / cutover / ถามทีม platform

# ตรวจสอบความถูกต้องและการตัดสวิตช์ (cutover)

> **ไฟล์นี้คืออะไร** — วิธีพิสูจน์ว่า pipeline ใหม่ใน ODI ให้ผลเท่ากับของเดิมใน Blendata
> ก่อนจะเลิกใช้ของเดิม พร้อมแบบคำถามถึงทีม platform/DBA และแบบบันทึกการตัดสินใจ
> **อ่านตอนไหน** — หลัง import สำเร็จ ก่อนเอาขึ้นใช้งานจริง และตอนเตรียมคำถามไปถามทีมอื่น
>
> **ทำไมต้องมีไฟล์นี้** — `knowledge/lessons-learned.md` ตรวจว่า *ไฟล์* ถูก ไฟล์นี้ตรวจว่า *ตัวเลข* ถูก
> package ที่ import ผ่าน รันจบ ไม่มี error และให้ตัวเลขผิด คือความล้มเหลวที่แพงที่สุด
> เพราะไม่มีใครรู้จนกว่าจะมีคนทักถึงรายงาน

## E1. ลำดับการตรวจ 4 ระดับ

ทำเรียงกัน ระดับหลังไม่ทดแทนระดับก่อน

### ระดับ 1 — จำนวนแถวตรงกัน

```sql
-- ฝั่งเดิม (Blendata)
SELECT COUNT(*) FROM <blendata_schema>.<target_table>;

-- ฝั่งใหม่ (Oracle/ODI)
SELECT COUNT(*) FROM <target_table>;
```

ทำทุกตารางปลายทางที่ย้ายมา ต่างกันแม้แถวเดียวต้องอธิบายให้ได้ก่อนไปต่อ

### ระดับ 2 — ค่ารวมของคอลัมน์ตัวเลขตรงกัน

**อย่าดูแค่ `SUM`** — ผลบวกกลบกันเองได้ ให้ดู 4 ค่าพร้อมกัน

```sql
SELECT COUNT(*), SUM(<measure>), MIN(<measure>), MAX(<measure>), AVG(<measure>)
FROM <target_table>;
```

ทำกับทุกคอลัมน์ตัวเลขที่เกิดจาก transform (ยอดเงิน, ยอดรวม, ตัวนับ) รันสองฝั่งแล้ว diff

### ระดับ 3 — เทียบรายแถว

สุ่ม key มา **20–50 ค่า โดยเลือกให้ครอบคลุมทุกสาขาของ `CASE`** ที่มีใน SQL
(เช่น ถ้า logic แตกตาม `pay_type` ต้องมี key ของทุก `pay_type` รวมค่าที่พบยาก)
แล้วเทียบ **ทั้งแถว** ไม่ใช่แค่คอลัมน์ที่สนใจ

เหตุผล: ค่ารวมในระดับ 2 กลบความผิดที่หักล้างกันเองได้ แถวเดียวที่ผิดสองที่ในทิศตรงข้าม
จะผ่านระดับ 1 และ 2 ไปได้สบาย

**ข้อมูลทดสอบต้องมีแถวผิดรูปแบบที่ "อ่านได้" ด้วย (`knowledge/lessons-learned.md` L34)** สำหรับทุกคอลัมน์ที่ SQL
parse text เป็นวันที่/เวลา ต้องมีอย่างน้อยหนึ่งแถวที่ค่า**สั้นกว่า pattern** (เช่น `20260827` ทั้งที่ pattern คือ
`yyyyMMddHHmmss`) และอย่างน้อยหนึ่งแถวที่ครบความยาวแต่เป็นวันที่เป็นไปไม่ได้ (เดือน 13) แถวที่เป็นตัวอักษรล้วนไม่พอ
เพราะ Oracle โยน error เองจนเห็นชัด ส่วนแถวสั้นกว่า pattern Oracle เติมศูนย์ให้เงียบๆ จึงหลุดเป็นแถวดี — เคสนี้
ทำให้ valid ได้ 18 แถวแทน 17 โดยไม่มี error ใดๆ และจับได้เพราะเทียบจำนวนแถวกับผลของ Blendata เท่านั้น

### ระดับ 4 — รันคู่ขนานครบหนึ่งรอบธุรกิจ

รันทั้งสอง pipeline ขนานกัน **อย่างน้อยหนึ่งรอบเต็มตามจังหวะจริงของข้อมูล**
(รายวัน/รายเดือน แล้วแต่ว่าข้อมูลมาเป็นรอบอะไร) ก่อนตัดสวิตช์

เหตุผล: การรันทดสอบครั้งเดียวไม่เจอเคสที่โผล่เฉพาะบางช่วง — batch สิ้นเดือน,
`pay_type` ที่พบน้อย, partition ที่มาช้า, วันที่ข้อมูลขาด

## E2. จุดที่ต้องระวังเป็นพิเศษเมื่อ Blendata → Oracle

ความต่างเหล่านี้ทำให้ตัวเลขเพี้ยนได้โดยไม่มี error — ตรวจตรงๆ อย่ารอให้ระดับ 1–3 จับ

| เรื่อง | ทำไมเพี้ยน | ตรวจยังไง |
|---|---|---|
| `''` กับ `NULL` | Oracle เก็บ `''` เป็น NULL — เงื่อนไข `= ''` เป็นเท็จเสมอ | นับแถวที่คอลัมน์นั้น `IS NULL` ทั้งสองฝั่ง |
| NULL ใน `concat` / `\|\|` | Spark คืน NULL ถ้ามีตัวใดเป็น NULL, Oracle มองเป็นค่าว่าง | นับ key ที่เป็น NULL ทั้งสองฝั่ง โดยเฉพาะคีย์ที่ใช้ join |
| `ORDER BY` ที่มี NULL ใน dedup | `NULLS FIRST`/`NULLS LAST` default ต่างกัน ผู้ชนะของ `ROW_NUMBER()` เปลี่ยน | เทียบแถวที่ถูกเลือกสำหรับ key ที่มีค่า NULL |
| `date_sub`/`date_add` แล้วไปเทียบกับ partition ละเอียดกว่าวัน | ผลเป็น DATE ตัดเวลาทิ้ง guard จึงเริ่มที่เที่ยงคืน | เทียบจำนวนแถวที่ขอบของช่วงเวลา |
| `CAST` ที่ Oracle strict แต่ Spark lenient | Spark คืน NULL, Oracle ตายทั้ง statement หรือ (ถ้าใส่ `DEFAULT NULL ON CONVERSION ERROR`) กลบ error ที่ควรถูกปฏิเสธ | นับแถวที่คอลัมน์ผลลัพธ์เป็น NULL ทั้งสองฝั่ง |
| `to_timestamp` ที่ input สั้นกว่า pattern | Spark คืน NULL, Oracle เติมศูนย์ให้เป็นวันที่ (แม้มี `DEFAULT NULL ON CONVERSION ERROR`) แถวผิดรูปแบบหลุดเป็นแถวดี | ใส่แถวทดสอบที่ค่าสั้นกว่า pattern แล้วเทียบสถานะ (เช่น `TYP` vs `MAP`) กับ Blendata รายแถว — ดู D-R8 / L34 |
| `TRUNCATE` แทน `DELETE` | `TRUNCATE` commit ทันที rollback ไม่ได้ | ถ้าการรันครึ่งทางแล้วล้มเหลวเป็นเรื่องที่รับไม่ได้ ต้องเปลี่ยนเป็น `DELETE` |
| **overwrite ที่เดิมผูกกับ partition** | `TRUNCATE TABLE` ลบทุก partition ไม่ใช่แค่ของรอบนี้ — **ระดับ 1 (นับแถว) จะผ่านถ้าเทียบเฉพาะ partition ของรอบที่เพิ่งรัน** | นับแถวแยกราย partition key **ของทั้งตาราง** ทั้งสองฝั่ง ไม่ใช่นับรวม ⚠️ ตรวจ**ก่อน**รันครั้งแรก ไม่ใช่หลัง — `TRUNCATE` ย้อนกลับไม่ได้ (`knowledge/lessons-learned.md` L29) |
| **NLS ของ session ที่ agent รัน** | `TO_DATE`/`TO_NUMBER` ที่ไม่มี format mask ให้ผลต่างกันระหว่าง session ของ agent กับของคนที่เทส — ได้วันที่หรือตัวเลขผิดโดยไม่มี error | รัน SQL ก้อนเดิมผ่าน **ODI agent** แล้วเทียบกับผลที่ได้จาก SQL Developer อย่าถือว่า "คนเทสผ่านแล้ว" เป็นหลักฐาน (`knowledge/lessons-learned.md` L30) |
| **ค่า Spark config ที่ไม่ตรงกับที่สมมติ** | ผลของ SQL เดิมขึ้นกับ `ansi`, `timeParserPolicy`, `escapedStringLiterals`, `session.timeZone` — ถ้าค่าที่ใช้แปลงไม่ตรงกับ Blendata จริง ตัวเลขเพี้ยนโดยไม่มี error | ใช้แถวขอบใน E7 (วันที่ผิดรูป, สตริงมี backslash, `now()` ที่ข้ามเที่ยงคืน) แล้วเทียบกับ Blendata รายแถว — ดู D-R9 |
| ความกว้างของ column ปลายทาง | การแปลง `CAST(x AS STRING)` → `VARCHAR2(4000)` กว้างเผื่อไว้ แต่ตารางจริงอาจแคบกว่า | เทียบความยาวสูงสุดของค่าจริงกับความกว้างของคอลัมน์ |

**quirk ของ Spark ที่จงใจคงไว้ ต้องบอกผู้ตรวจก่อน** — เอกสารเทสของงานเดิมมักบันทึก
พฤติกรรมแปลกๆ ไว้เป็น "ผลลัพธ์ที่คาดหวัง" การ "แก้ให้ถูก" เงียบๆ ตอนแปลงจะทำให้จำนวนแถว
ที่คาดหวังไม่ตรง แล้วเสียเวลาไล่หาว่าใครผิด

## E3. แบบ sign-off ก่อน cutover

- [ ] จำนวนแถวตรงกันทุกตารางที่ย้ายมา
- [ ] ค่ารวม (COUNT / SUM / MIN / MAX / AVG) ตรงกันทุกคอลัมน์ตัวเลข ภายในค่าความคลาดเคลื่อนที่ตกลงกันไว้ — **ต้องตกลงตัวเลขนี้กับเจ้าของงานก่อน** ปกติคาดหวังว่าตรงเป๊ะ เว้นแต่มีเรื่องปัดเศษทศนิยมที่รู้อยู่แล้ว
- [ ] เทียบรายแถวผ่านครบทุกสาขา `CASE`
- [ ] logic แบบ incremental / CDC (ถ้ามี) ยืนยันแล้วว่าหยิบเฉพาะแถวใหม่หรือที่เปลี่ยน
- [ ] รันคู่ขนานครบหนึ่งรอบธุรกิจแล้ว ผลตรงกัน
- [ ] ตารางเวลาใน ODI Scheduler ตรงกับจังหวะเดิมของ Blendata
- [ ] Scenario ถูก generate แล้วและชี้ไป Package เวอร์ชันที่ถูกต้อง
- [ ] Topology ที่ต้องตั้งเองตั้งครบแล้ว + ใส่ credential แล้ว
- [ ] ทาสก์ที่ถูกตัดออกจาก package มีแผนรองรับ (รันแยก / ทำมือ / ยกเลิก) และเจ้าของงานรับทราบ
- [ ] **แผน rollback ยืนยันแล้ว** — ถ้าต้องกลับไปใช้ Blendata ทำยังไง ข้อมูลที่ ODI เขียนไปแล้วจัดการยังไง
- [ ] ผล import ครั้งแรกถูกบันทึกไว้ (ผ่าน/ไม่ผ่าน + error ถ้ามี)
- [ ] **ทุกทาสก์ overwrite ยืนยันขอบเขตการลบข้อมูลแล้ว** — ทั้งตาราง หรือเฉพาะ partition
      และเจ้าของงานรับทราบ **ต้องติ๊กข้อนี้ก่อนรันครั้งแรก ไม่ใช่ก่อน cutover**
      (`knowledge/lessons-learned.md` L29 — `TRUNCATE` ย้อนกลับไม่ได้)
- [ ] **ทุก `MERGE` ยืนยันแล้วว่า `USING` คืนหนึ่งแถวต่อหนึ่งคีย์** ด้วยข้อมูลจริงของรอบทดสอบ
- [ ] **SQL ถูกรันผ่าน ODI agent จริงแล้ว** ไม่ใช่ผ่านแค่ SQL Developer (เรื่อง NLS)

## E4. คำถามที่ต้องถามทีม platform / DBA

รวบรวมไว้ถามครั้งเดียว อย่าถามทีละข้อ ทีมพวกนี้ตอบช้าและงานจะค้าง

**เรื่อง repository และสิทธิ์**

1. Work repository ที่จะ import คืออันไหน (ชื่อ / host / SID) และ dev-uat-prod แยกกันยังไง
2. ใครมีสิทธิ์ Smart Import ในแต่ละ repo และต้องขออนุมัติแบบไหน
3. มีข้อกำหนดเรื่องชื่อ Project / Folder / Package ของทีมไหม

**เรื่อง Topology**

4. Logical Schema ที่ควรใช้ชื่ออะไร และ Context ที่ใช้จริงในแต่ละ environment
5. ถ้างานต้องเขียนออกไประบบที่ไม่ใช่ Oracle (เช่น SQL Server) มี Data Server นั้นใน Topology แล้วหรือยัง ถ้ายัง ใครเป็นคนสร้างและใช้เวลานานแค่ไหน
6. credential ของ connection เหล่านั้นเก็บที่ไหน ใครใส่ (**เราไม่ใส่ให้ และไม่ขอดู**)

**เรื่องฐานข้อมูลปลายทาง**

7. ตารางปลายทางทุกตัวมีอยู่จริงแล้วหรือยัง ถ้ายัง ใครสร้างและสคริปต์ DDL ต้องผ่านใคร
8. สิทธิ์ของ user ที่ ODI ใช้ — `SELECT` / `INSERT` / `DELETE` / `TRUNCATE` ครบไหม
   (`TRUNCATE` ต้องการสิทธิ์ต่างจาก `DELETE` — ถ้าไม่มีจะพังตอนรัน ไม่ใช่ตอน import)
9. ตารางปลายทางมี partition ไหม ถ้ามี `TRUNCATE TABLE` ทั้งตารางยังเป็นสิ่งที่ต้องการหรือเปล่า
   ⚠️ **ข้อนี้ต้องถามให้ได้คำตอบก่อนรันครั้งแรก ไม่ใช่ตอน cutover** — ถ้างานเดิมเขียนทับเฉพาะ
   partition (`sinkOption.partitions` ไม่ว่าง) การ `TRUNCATE` ทั้งใบลบข้อมูลย้อนหลังถาวร
   และย้อนกลับไม่ได้ จุดตัดสินอยู่ที่ **I14** (`knowledge/lessons-learned.md` L29)
   ถ้าตารางมี partition จริง ขอชื่อ partition กับ partition key มาด้วยเลย เผื่อเลือกทาง
   `ALTER TABLE … TRUNCATE PARTITION`
10. มี index / constraint ที่ต้อง disable ก่อน load ปริมาณมากไหม
    และ **มี foreign key ที่ enabled ชี้เข้าตารางที่เราจะ `TRUNCATE` ไหม** — ถ้ามี `TRUNCATE`
    จะตายด้วย `ORA-02266` ต้องเปลี่ยนเป็น `DELETE` (`knowledge/lessons-learned.md` L29)
    **เราไม่ disable constraint ให้ และไม่ขอให้ disable** — นั่นเป็นการเปลี่ยนสภาพฐานข้อมูล
11. **NLS ของ session ที่ ODI agent ใช้ต่อ** — `NLS_DATE_FORMAT` และ
    `NLS_NUMERIC_CHARACTERS` ตั้งไว้เป็นอะไร และตั้งที่ไหน (JVM ของ agent, Data Server
    ช่อง `OnConCmd`, หรือ default ของ database) ใช้ตอบว่า SQL ที่คนเทสผ่านแล้วจะรันเหมือนเดิม
    ตอน agent รันหรือเปล่า (`knowledge/lessons-learned.md` L30)

**เรื่องการรันและการติดตาม**

12. ODI Agent ตัวไหนจะรัน scenario นี้ และ schedule ตั้งที่ไหน
13. ถ้า job ล้ม ใครได้รับแจ้ง ผ่านช่องทางอะไร
14. นโยบาย retry คืออะไร รันซ้ำได้ปลอดภัยไหม (**เกี่ยวโดยตรงกับ I15 เรื่อง step สถานะ**
    ถ้า control table ยังเป็น placeholder การรันซ้ำอาจประมวลผลข้อมูลเดิมซ้ำ)

**เรื่องการทดสอบ**

15. มี environment ที่มีข้อมูลเหมือนจริงให้ทดสอบไหม
16. รันคู่ขนานกับ Blendata ได้ไหม หรือจะชนกันที่ตารางปลายทาง

## E5. แบบบันทึกการตัดสินใจ

ทุกครั้งที่เจอทางแยกที่ผู้ใช้ต้องเลือก **ให้บันทึกเป็นเอกสารสั้นๆ ไม่ใช่แค่ตอบในแชท**
เพราะอีกสามเดือนจะไม่มีใครจำได้ว่าทำไมถึงเลือกแบบนั้น

```markdown
# การตัดสินใจ: <หัวข้อสั้นๆ>
วันที่: YYYY-MM-DD   ผู้ตัดสิน: <ชื่อ>   สถานะ: เสนอ / ตกลงแล้ว / ยกเลิกแล้ว

## เรื่องที่ต้องตัดสิน
<หนึ่งย่อหน้า ว่าทางแยกคืออะไร และทำไมถึงตัดสินเองไม่ได้>

## ทางเลือก
### ทาง A — <ชื่อ>
ข้อดี: · ข้อเสีย: · ความเสี่ยง: · ใครได้รับผลกระทบ:
### ทาง B — <ชื่อ>
ข้อดี: · ข้อเสีย: · ความเสี่ยง: · ใครได้รับผลกระทบ:

## ที่เลือก และเหตุผล
<ทางไหน เพราะอะไร ถ้ามีสมมติฐานที่ต้องเป็นจริง ให้เขียนไว้ด้วย>

## สิ่งที่ต้องทำต่อ
```

## E6. รายงานปิดงานที่ต้องส่งพร้อมไฟล์

อย่าส่ง XML เปล่า ต้องมีรายการเหล่านี้ในที่เดียว

1. **ทาสก์ที่ตัดออก** — ชื่อ + เหตุผล + ใครต้องทำอะไรต่อ
2. **placeholder ที่ยังเหลือ** — โดยเฉพาะ step สถานะ พร้อมผลกระทบถ้ารันซ้ำ
3. **Topology ที่ต้องตั้งเอง** — connection อะไร ใครตั้ง
4. **Scenario** — ต้อง generate เองใน Studio (Package → Generate Scenario)
5. **ค่าที่เดาไม่ได้จึงถาม และคำตอบที่ได้** — ให้คนตรวจย้อนกลับได้
6. **ค่าที่มาจากตัวอย่างเดียวใน reference** — `SqlIndGrp` หรือ flag ที่ยังไม่ใช่กฎ
7. **quirk ของ Spark ที่คงไว้โดยตั้งใจ**
8. **ผลตรวจตาม `knowledge/lessons-learned.md`** — ข้อไหนผ่าน ข้อไหนข้ามและเพราะอะไร
9. **สิ่งที่ยังไม่ได้ทดสอบ** — พูดตรงๆ ดีกว่าให้คนอื่นไปเจอเอง
10. **ตารางที่ column list มาจากโหมดเดา** — ระบุชื่อเป็นรายใบ **แยกจาก**ตารางที่มี DDL จริง
    ห้ามรวมเป็นก้อนเดียวกับ "ตรวจไม่ได้" (checklist ข้อ 35)
11. **วิธีเคลียร์ข้อมูลของทุกทาสก์ overwrite** — ใบไหน `TRUNCATE` ทั้งตาราง
    ใบไหน `DELETE … WHERE <partition key>` ใบไหน `TRUNCATE PARTITION` และใครเป็นคนยืนยัน
    **ถ้าใบไหนเลือก `TRUNCATE` ทั้งตารางทั้งที่งานเดิมผูกกับ partition ต้องเขียนตรงๆ ว่านั่นคือ
    การตัดสินใจลบข้อมูลย้อนหลัง** ไม่ใช่ปล่อยให้อ่านเอาเองจาก SQL (`knowledge/lessons-learned.md` L29)
12. **`MERGE` ทุกตัวที่ยังไม่ได้ยืนยันว่า `USING` ไม่คืนคีย์ซ้ำ** — เป็นความเสี่ยง `ORA-30926`
    ที่รอโผล่ตอนข้อมูลจริงเปลี่ยน (`knowledge/lessons-learned.md` L31)

## E7. ชุด SELECT ตรวจผลเทียบ Blendata (`output/validation/`)

> **ใหม่ใน v18** — เดิม E1 บอกหลักการ 4 ระดับ แต่ไม่มีของพร้อมใช้ ผลคือการเทียบมักหยุดแค่ "รันได้ไม่ error"
> ซึ่งไม่พิสูจน์ว่าตัวเลขถูก (L34: ได้ 18 แถวแทน 17 โดยไม่มี error เลย)

**ส่งมอบเป็นไฟล์เดียว** `output/`output/validation/` พร้อมกับชุดอื่น โดย agent เป็นคนแทนค่าให้ครบจากคำตอบ I3/I4/I14
(กฎการถามข้อ 13) — ห้ามส่ง placeholder เปล่า · คนเป็นคนรันและวางผลกลับ (ข้อห้ามใน `migration-rules.md` หัวข้อ 7) · ทุกคำสั่งเป็น `SELECT`

**ขอบเขตของ "ตารางที่ต้องเทียบ"** — ตารางปลายทางทุกตัวที่ package เขียน (จาก `table-inventory.md`) ไม่ใช่ตารางต้นทาง

**ชุดคำสั่ง** (แสดงรูปแบบ — `{SCHEMA}`/`{TABLE}`/`{...}` agent แทนให้เป็นค่าจริงทุกตัวก่อนส่ง)

```sql
-- L1: จำนวนแถว (Oracle) -- ฝั่ง Blendata: SELECT COUNT(*) FROM {TABLE}
SELECT '{TABLE}' AS table_name, COUNT(*) AS row_count FROM {SCHEMA}.{TABLE}

-- L1b: จำนวนแถวแยกราย partition key ของทั้งตาราง (บังคับถ้า I14 พบ overwrite ที่ผูกกับ partition — L29)
SELECT {PARTITION_KEY}, COUNT(*) AS row_count FROM {SCHEMA}.{TABLE} GROUP BY {PARTITION_KEY} ORDER BY 1

-- L2: ผลรวมคอลัมน์ตัวเลข (ใส่ทุกคอลัมน์ตัวเลขที่ธุรกิจใช้)
SELECT SUM({NUM_COL_1}) AS sum_1, SUM({NUM_COL_2}) AS sum_2 FROM {SCHEMA}.{TABLE}

-- L3: แถวต่อแถว -- ทำ hash ต่อแถวพร้อมคีย์ แล้วเทียบสองฝั่งด้วยคีย์ (ส่งออกเป็น CSV ทั้งสองฝั่ง)
SELECT {KEY_COL},
       LOWER(RAWTOHEX(STANDARD_HASH(
         NVL(TO_CHAR({COL_1}),'<NULL>')||'|'||NVL(TO_CHAR({COL_2}),'<NULL>')||'|'||NVL(TO_CHAR({TS_COL},'YYYYMMDDHH24MISS'),'<NULL>'),
         'MD5'))) AS row_hash
FROM {SCHEMA}.{TABLE}
-- ฝั่ง Blendata (Spark): ต้อง normalize NULL แบบเดียวกัน
-- SELECT {KEY_COL}, md5(concat(coalesce(cast({COL_1} AS string),'<NULL>'),'|',coalesce(cast({COL_2} AS string),'<NULL>'),'|',coalesce(date_format({TS_COL},'yyyyMMddHHmmss'),'<NULL>'))) AS row_hash FROM {TABLE}

-- L4: จำนวน NULL ของคอลัมน์ที่ semantics ต่างกัน (`''` กับ NULL, `concat`) -- ทั้งสองฝั่ง
SELECT SUM(CASE WHEN {COL} IS NULL THEN 1 ELSE 0 END) AS null_count FROM {SCHEMA}.{TABLE}

-- L5: การกระจายของสถานะ/ประเภท (ถ้ามีคอลัมน์ status/type) -- เทียบสองฝั่ง
SELECT {STATUS_COL}, COUNT(*) FROM {SCHEMA}.{TABLE} GROUP BY {STATUS_COL} ORDER BY 1
```

**ถ้า I17b เลือกเปิด error log** — เพิ่มข้อนี้ทุกตารางที่มี `ERR_`:

```sql
-- L6: แถวที่ถูก reject ลง error log (ต้องเป็น 0 หรืออธิบายได้ทุกแถว)
SELECT ORA_ERR_NUMBER$, ORA_ERR_MESG$, ORA_ERR_TAG$, COUNT(*) AS row_count
FROM {SCHEMA}.{ERR_TABLE}
GROUP BY ORA_ERR_NUMBER$, ORA_ERR_MESG$, ORA_ERR_TAG$
```

⚠️ **ทำไม L6 บังคับ** — `LOG ERRORS ... REJECT LIMIT UNLIMITED` ทำให้ statement *ไม่ล้ม* แม้มีแถวเสีย ODI รายงาน step สำเร็จ
ทั้งที่แถวบางส่วนหายไป ถ้าไม่ตรวจ L6 จะไม่มีใครรู้ (L32)

**ข้อกำหนดข้อมูลทดสอบ** (รวมกับของ E2 เดิม) — ต้องมีแถวขอบอย่างน้อยหนึ่งแถวต่อเรื่องที่ใช้: ค่าสั้นกว่า pattern ของวันที่ (L34),
วันที่ผิดรูปอื่น (ถ้า `timeParserPolicy` ไม่ทราบ), สตริงที่มี `\` (ถ้า regex และ `escapedStringLiterals` ไม่ทราบ), ค่า `''` และ NULL,
คีย์ที่เป็น NULL (ถ้าใช้ใน join), แถวใกล้เที่ยงคืน (ถ้ามี `now()` และผล timezone ที่ I10 ข้อ 6 พบว่าไม่ตรง)

**เกณฑ์ผ่าน** — L1, L1b, L2, L4, L5 ตรงกันทั้งสองฝั่ง · L3 ไม่มีคีย์ที่ hash ต่าง · L6 = 0 (หรืออธิบายทุกแถวแล้ว) · ส่วนต่างทุกจุดที่ยอมรับ
ต้องมีแถวใน "บันทึกการตัดสินใจ" ของ `status/MIGRATION_STATUS.md` (`knowledge/reference/deliverables.md` (หัวข้อ migration-state)) — **ห้ามเปลี่ยนสถานะ "ตรวจตัวเลขแล้ว" จนกว่าผู้ใช้ยืนยันผลเอง**

**ไม่ได้ยืนยัน** — รูปแบบ L3 (hash ต่อแถว) เป็นแนวทางที่ออกแบบใหม่ ยังไม่เคยรันกับงานจริง ผู้ใช้อาจต้องปรับ
การ normalize ชนิดข้อมูลให้ตรงกันสองฝั่ง ถ้า hash ไม่ตรงทั้งที่ข้อมูลดูเหมือนกัน ให้เทียบทีละคอลัมน์ก่อนสรุปว่าข้อมูลต่าง

**วิธีได้ "ผลที่ควรได้" และ mock data สำหรับเทียบ** — L1–L6 เทียบ Oracle กับ Blendata จริง ส่วนการเทสต์ก่อนขึ้นระบบด้วยข้อมูลจำลองใช้
`knowledge/reference/test-method.md` (รัน Spark SQL เดิมบน seed เพื่อได้ expected, สร้าง mock Oracle จาก seed เดียวกัน, เทียบด้วย `compare_tables.py`) — สองอย่างนี้เสริมกัน ไม่ใช่ทดแทนกัน
